# Відео: запис, зберігання, обробка

Камера над стійкою пише безперервно. Відео потрібне для двох різних речей, і
плутати їх не можна:

1. **Охорона** — повний архів 7 діб, дивиться людина, коли щось сталося.
2. **Аналітика** — події «підійшли / скільки / скільки простояли», далі в
   геймифікацію і в звірку з чеками. Дивиться машина, і не поспішаючи.

Перше вимагає повноти, друге — процесора. Тому вони розділені по всьому
ланцюжку: різні бакети, різні строки, різні дроплети.

---

## Загальна схема

```
  ТОЧКА                        CLOUDFLARE              DIGITALOCEAN (VPC, FRA1)

┌──────────────┐
│  Tapo C100   │            ┌───────────────┐        ┌────────────────────┐
│   RTSP :554  │            │   R2 video    │  pull  │ дроплет  analysis  │
│   SD 16 ГБ   │            │  7 діб, LC    │◀──────▶│ 1 vCPU · 2 ГБ      │
└──────┬───────┘            └───────▲───────┘        │ worker             │
       │ rtsp (тільки LAN)          │                │ ⛔ публічних       │
┌──────▼───────┐   S3 PUT, 1 год    │                │    портів немає    │
│  edge-вузол  │────────────────────┘                └─────────┬──────────┘
│ ffmpeg -copy │                                               │
│ буфер, USB   │            ┌───────────────┐                  │ VPC
└──────┬───────┘            │  R2 evidence  │                  │
       │                    │ кадри, кліпи  │◀────┐            │
       │ POST /ingest       └───────────────┘     │            │
       │                                          │            │
       │                    ┌───────────────┐     │            │
       │                    │  R2 backup    │◀──┐ │            │
       │                    │  WAL + dump   │   │ │            │
       │                    └───────────────┘   │ │            │
       │                    ┌───────────────────┴─┴────────────▼──┐
       └───────────────────▶│      дроплет  public  :443          │
                            │ api·ws·checkbox·overseer·glitchtip  │
┌──────────────┐            │ redis · ключ R2 · POSTGRES у докері │
```

Відео **ніколи не йде через дроплети**. Edge-вузол вантажить байти прямо в R2,
а в бекенд летить лише рядок метаданих. Це і дешевше, і знімає з публічного
дроплета весь відеотрафік.

## Чому два дроплети

> **Поки що — один** (12.10.2026). Воркер крутиться в прод-стеку на `public`
> поруч з усім іншим, під стелею `cpus: 0.5` і `mem_limit: 600m`
> (`docker-compose.prod.yml`). Це стало можливим завдяки гейту по руху:
> більшість хвилин перед камерою ніхто не ходить, і такий сегмент коштує
> ~2 с замість ~25. Заміри на наших записах: пів ядра дає 2,4× реального часу
> на найзавантаженішому сегменті, пік памʼяті — 101 МБ python + до 236 МБ
> ffmpeg на 1080p. Аргументи нижче лишаються в силі — коли точок стане
> кілька або ліміт почне впиратись, воркер переїжджає на `analysis` без змін
> у коді: черга в постгресі, а не в процесі.

| | `public` | `analysis` |
|---|---|---|
| Розмір | 2 vCPU / 4 ГБ, $24 | 1 vCPU / 2 ГБ, $12 |
| Що крутить | `api`, `ws`, `checkbox`, `overseer`, `scheduler`, `glitchtip`, `redis`, **postgres**, видача тимчасових ключів R2 | `worker` і більше нічого |
| Публічні порти | 80/443 | **немає жодного** |
| Профіль навантаження | багато коротких запитів, латентність важлива | довгі CPU-жери, латентність не важлива |
| Що станеться при перевантаженні | лягає кіоск і застосунок | нічого не лягає, черга просто росте |

База живе в докері на `public` разом з рештою стека — так само, як зараз у
`docker-compose.yml`. Це свідома економія на старті; умови переїзду на керовану
базу — нижче в розділі «База».

> На `public` найбільший споживач памʼяті після постгреса — **glitchtip з
> celery-воркером** (Django, легко пів гігабайта). Якщо 4 ГБ почне тиснути,
> першим виїжджає саме він, а не щось потрібне.

Обробка відео — принципово нестабільне навантаження: ffmpeg може зʼїсти всю
памʼять на битому сегменті, модель може зависнути, диск може забитись
тимчасовими файлами. Тримати це поруч із кіоском не можна. Розділення дає
головне: **`analysis` можна перезавантажити, ресайзнути чи зламати посеред дня —
клієнти цього не помітять.**

Воркер додатково обмежений, щоб не вбити власний дроплет — на 1 vCPU / 2 ГБ
це не формальність, а необхідність:

```yaml
  worker:
    cpus: 0.5          # на public; на окремому analysis можна 0.8
    mem_limit: 600m    # заміряний пік ~340 МБ (python + ffmpeg на 1080p)
    restart: unless-stopped
```

### Мережа

Обидва дроплети — в одному VPC, регіон **FRA1** (найближчий до нас із
європейських DO). Файрвол:

- `analysis` — inbound лише SSH з VPC або через Tailscale. Ніяких 80/443.
  Наружу йому треба тільки R2 і постгрес по приватній адресі.
- `public` — назовні відкриті 80/443 і SSH, більше нічого.
- Камера — **ніколи не пробрасувати 554 назовні.** Відкриті RTSP камер
  сканують масово. Камера спілкується лише з edge-вузлом у своїй LAN.

> ⚠️ **Перевірити перед першим деплоєм.** У поточному `docker-compose.yml`
> постгрес і редіс опубліковані як `ports: ["5432:5432"]` і `["6379:6379"]` —
> тобто на всі інтерфейси. На локальній машині це нормально, на публічному
> дроплеті це відкрита база в інтернет. Два виправлення, потрібні обидва:
>
> 1. Прив'язати до петлі й приватної адреси: `127.0.0.1:5432:5432`, а для
>    доступу з `analysis` — `10.x.x.x:5432:5432` (адреса у VPC).
> 2. Увімкнути **хмарний файрвол DigitalOcean**, а не `ufw`: докер пише свої
>    правила в iptables повз ufw, і порт лишається відкритим попри «заборонено».

### Скільки насправді треба дроплету аналізу

Обробка асинхронна — саме тому на ній можна економити. Ніхто не чекає
результату в реальному часі: відстали на дві години, наздогнали вночі.

Порахунок на **одну камеру** при семплінгу 2 fps:

| Крок | На 1 годину відео |
|---|---|
| Декодування 1080p15 (54 тис. кадрів) | ~3 хв CPU |
| Детекція, 7 200 кадрів × ~80 мс | ~10 хв CPU |
| **Разом** | **~13 хв CPU на 1 vCPU** |

Тобто запас приблизно **4,6× до реального часу**: добу відео одне ядро жує
близько пʼяти годин. З гейтом по руху — ще в кілька разів менше. Після триденного
обриву звʼязку черга розсмокчеться за ніч.

> **Заміряно 23.09.2026** на чорновому воркері й чужому CCTV-відео
> (`backend/worker/README.md`). Декод підтвердився: 1080p15 із семплінгом —
> 2,3 с на хвилину відео, тобто ~55 хв на добу. А от 80 мс на кадр — це
> числа моделі з входом 320, а не «YOLO-n» взагалі: те саме yolo11n на 640
> дає 269 мс, на 448 — 143, на 448 з int8-квантизацією — 112. Тому в образі
> за замовчуванням саме **448 + int8**, і запас виходить ближче до **2×**,
> а не 4,6× (ще й на ядрі ноутбука — на shared vCPU буде гірше). З гейтом
> по руху цього все одно вистачає: нерухомий сегмент коштує 1 с замість 13.

Мінімум, який реально працює — **1 vCPU / 2 ГБ / 50 ГБ, $12/міс**:

- **$4 (512 МБ) і $6 (1 ГБ) не годяться.** ONNX-рантайм із моделлю тримає
  ~0,5 ГБ, ffmpeg ще ~0,2, пітонівський рантайм ~0,3 — гігабайта не вистачить,
  і ловитимемо OOM на випадковому сегменті.
- Обовʼязково **swap 2 ГБ** — копійчана страховка від піків.
- Диска 50 ГБ вистачає з головою: воркер тримає один сегмент за раз (~6 МБ)
  плюс моделі.
- Basic — shared CPU, DO сам описує його як «ideal for bursty applications».
  Наш профіль саме такий; для рівного 100 % завантаження цей клас не
  призначений, але ми туди й не збираємось.

Коли впремося і треба буде **2 vCPU / 4 ГБ ($24)**: друга камера на точці, або
відмова від гейта по руху, або аналіз на всіх 15 fps замість семплінгу 2 (знімаємо ми
15 і так — рідший тут саме розбір, а не запис). Це видно заздалегідь по
графіку лагу черги, а не за фактом втрати даних.

## Edge-вузол на точці

Потік — **95 КБ/с**. Це настільки мало, що процесор тут майже ні до чого:

| Ресурс | Треба | Стеля Pi 1 |
|---|---|---|
| Мережа (USB-Ethernet) | ~0,2 МБ/с сумарно | ~4–8 МБ/с |
| CPU на remux | одиниці відсотків | 700 МГц ARMv6 |
| RAM | 20–40 МБ | 384 МБ (після `gpu_mem=128`), частину з них тримає кіоск |

Тому **суміщення із кіосковим Pi 1 не виключене** — але ризики лежать не там,
де здається:

1. **Памʼять.** Кіоск — нативний `kiosk`: у спокої це десятки мегабайт
   із доступних 384, але під записом його памʼять на пристрої ще не заміряна.
2. **Системна SD-карта.** 8,2 ГБ на добу вбʼють її за місяці. Писати **тільки
   на USB-флешку**, з `noatime`. 32 ГБ = 4 доби буфера, знос 0,26 перезапису на
   добу — це флешка витримає роками.
3. **Raspbian 9 Stretch, ядро 4.14.** EOL, репозиторії в архіві. Все сучасне
   доведеться або збирати з джерел, або не використовувати.

Запис зобовʼязаний бути фізично не здатний придушити кіоск — кіоск це шлях до
грошей, запис ні:

```ini
[Service]
Nice=10
IOSchedulingClass=idle
MemoryMax=96M
Restart=always
RestartSec=5
```

⚠️ Ці ліміти написані під окремий systemd-юніт. У керованому стеку
(`raspberry-pi.md` §2) запис — рядок у `components.conf`, дитина супервізора,
тож `MemoryMax` на нього не діє: пріоритет можна задати `nice` і `ionice` при
запуску, а межу памʼяті — ні. Як обмежувати памʼять запису — відкрите питання
до того, як вмикати `recorder`.

> **Порядок дій: спершу стіл, потім точка — пройдено 17.08.2026.** На Pi 1 з
> кіоском і ffmpeg поруч: меню тримає 52 fps і під час запису,
> `ffmpeg -c copy` бере 4,3 % CPU, 20 сегментів із 20 (`roadmap.md`,
> `raspberry/pi/README.md`). Окремий вузол не купуємо. Хвости заміру — RTSP із
> справжнього джерела, USB-флешка, довгий прогін — у кроці 1-біс `roadmap.md`.

### Запис

```bash
ffmpeg -nostdin -loglevel warning \
  -rtsp_transport tcp -use_wallclock_as_timestamps 1 \
  -i "rtsp://$CAM_USER:$CAM_PASS@$CAM_IP:554/stream1" \
  -map 0 -c copy \
  -f segment -segment_time 60 -reset_timestamps 1 \
  -segment_format matroska \
  -strftime 1 "$BUF/%Y%m%dT%H%M%SZ.mkv"
```

**Тут не відбувається ні декодування, ні кодування.** `-c copy` — це demux +
remux: ffmpeg дістає вже стиснені H.264-пакети з RTSP і перекладає їх у
контейнер байт-у-байт. Транскодування немає ніде в ланцюжку — ні тут, ні в
хмарі, де воркер лише вибірково декодує окремі кадри для моделі.

Чому саме так:

| Прапорець | Навіщо |
|---|---|
| `-c copy` | без перекодування — одиниці відсотків ядра, а не 100 % |
| `-rtsp_transport tcp` | UDP на дешевій камері губить пакети й дає артефакти |
| `-map 0` | усі доріжки камери: відео й звук (див. «Звук» нижче) |
| `-segment_format matroska` | контейнер, який несе і H.264, і звук камери (`pcm_alaw`) без перекодування. Обрізаний живленням сегмент лишається читабельним до місця обриву: ffmpeg пише mkv кластерами, індекс у кінці лише прискорює перемотування (перевірено: перші 60 % файла — 60 % кадрів). MP4 у цьому місці вимагав би фокусів із `+frag_keyframe`. До 07.10.2026 тут був MPEG-TS — див. «Звук» |
| `-use_wallclock_as_timestamps` | камера без інтернету втрачає NTP і бреше про час; час беремо з вузла |
| `-strftime` | імʼя файла = час початку, далі не треба нічого парсити |

Запускати через systemd з `Restart=always` — камера періодично рве потік сама.
Різати ffmpeg може лише по ключових кадрах, тож сегменти будуть 60 с ±GOP.

**Як це зроблено (06.10.2026)** — компонент стеку `raspberry/pi/stack/recorder.sh`,
рядок у `components.conf`, дитина супервізора; приїжджає й оновлюється
релізом. На малині тільки перекладання пакетів — нічого не накладаємо й не
перекодовуємо (власник): та сама команда, що вище, плюс
`nice -n 10 ionice -c 3`.

**Звук (07.10.2026).** Спершу recorder звук відкидав (`-an`) і писав
MPEG-TS. Власник вирішив звук зберігати — з нього згодом можна буде щось
дістати, — і так само без перекодування. Звук C100 — `pcm_alaw` 8 кГц моно,
а MPEG-TS його без перекодування не несе: ffmpeg кладе доріжку туди як
«`bin_data`», і жоден плеєр її не грає. Тому контейнер змінено на Matroska:
вона бере і H.264, і A-law як є. Звук — 64 кбіт/с, ~0,5 МБ на хвилину
(~5 % до відео). Сегменти, записані раніше, лишаються `.ts` без звуку;
uploader і api приймають обидва.

На ffmpeg 5.1 це перевірено в контейнері, а на 3.2 зі Stretch — лише після
першого запуску на малині. Тому страховка: якщо ffmpeg одразу падає з
помилкою заголовка чи кодека («Could not write header», «codec tag», «not
supported»), recorder пише рядок у лог і далі пише лише відео (`-map 0:v`)
до перезапуску компонента — запис без звуку кращий, ніж жодного. Обидва
сценарії прогнано в контейнері через recorder.sh (07.10.2026).

- **Камера** — `config/camera.env` на розділі `data` (шаблон
  `raspberry/pi/camera.env.example`): MAC і логін-пароль «акаунта камери»
  Tapo. Адресу камера бере по DHCP, тож recorder знаходить її за MAC в
  ARP-таблиці, а якщо там порожньо — пінгує підмережу партіями по 32.
  Статичну адресу в камері свідомо не ставимо: роутер про неї не знає і може
  видати її комусь іще, а камера зі старою статикою на новому роутері
  зникає зовсім. kyiv-01 — Tapo C100 v5, MAC `c0:3a:55:fc:7b:57`.
- **Спершу в RAM, на флешку — лише запас (15.10.2026).** ffmpeg пише в
  tmpfs (`RECORDER_RAM`, типово `/dev/shm/extrovert-video`), аплоудер бере
  готові сегменти звідти в першу чергу, і на флешці сегмент опиняється, лише
  коли заливка не встигає. Причина — шина: на Pi 1 Ethernet (потік камери),
  Wi-Fi (заливка) і флешка сидять на одному USB-контролері, з 15.10.2026 у
  режимі USB 1.1 (~8–9 Мбіт/с на практиці). Сегмент через флешку проходив
  шиною чотири рази — з камери, на флешку, з флешки, у Wi-Fi, — а з RAM
  двічі; кожна USB-передача ще й коштує процесора на перериваннях. У RAM
  лишаються `RECORDER_RAM_KEEP` (3) найсвіжіших готових, старші recorder
  щопів хвилини переносить на флешку фоновим процесом (копія під
  тимчасовим іменем, потім перейменування, час зміни зберігається), крім
  того, який саме читає аплоудер (`state/upload.current`). Аварійна межа —
  `RECORDER_RAM_MAX` (8, ~40 МБ): більше готових у RAM — найстаріші
  стираються з рядком у лозі; так буває, лише коли флешка не приймає копій,
  і без межі tmpfs з'їв би памʼять разом із кіоском. На зупинці компонента
  recorder переносить на флешку все з RAM, скільки встигне. **Ціна:**
  знеструмлення забирає те, що лежало в RAM, — у штатному ритмі це поточний
  сегмент і ще щонайбільше один, без інтернету — до трьох хвилин запису.
  Аплоудер у RAM-першому порядку: свіжі сегменти йдуть у R2 одразу, а хвіст
  на флешці доганяється в решту часу (найстаріші першими), тож поки хвіст є,
  в архіві R2 тимчасово бувають дірки. Порожній `RECORDER_RAM` — запис прямо
  на флешку, як раніше. Перевірено в контейнері зі справжнім ffmpeg і RTSP
  (mediamtx, H.264 + A-law): штатний шлях без жодного запису на флешку,
  обрив мережі (перенос після трьох готових), повернення (спершу RAM, потім
  флешка), зупинка (усе з RAM на флешці, кожен файл читається ffprobe),
  флешка, що не приймає копій (межа спрацьовує, рядок у лозі один), і
  відбракований сегмент із RAM (у `rejected/` на флешці копією).
- **Без флешки не пише.** Корінь під overlay живе в RAM, і запис у
  незмонтовану `/mnt/buf` за годину поклав би малину; флешка потрібна й для
  переносу з RAM.
- **Пароль у логи не потрапляє**: ffmpeg друкує адресу потоку разом з
  обліковими даними, recorder маскує їх (`rtsp://***@…`).
- **Будь-які символи в логіні й паролі.** `camera.env` читається буквально,
  а не через `.` (shell розгорнув би `$` — у логіні kyiv-01 стояло «$@»), а в
  адресу потоку логін і пароль ідуть із %-кодуванням. ffmpeg 3.2 на Stretch
  такі адреси розкодовує — перевірено на C100 kyiv-01 06.10.2026: H.264
  1920×1080 і звук `pcm_alaw`.
- **Збої камери**: сторожок перезапускає ffmpeg, якщо нового сегмента немає
  три інтервали; повтори — з паузою від 5 до 60 с і без однакових рядків у
  лозі, тож вимкнена на ніч камера лог не засипає.
- **Поки немає вивантаження**, флешка — архів по колу: менше 2 ГБ вільного —
  стираємо найстаріші сегменти.
- `video_ok` у телеметрії — чи є сегмент, молодший за 3 хв (у RAM, а якщо
  там порожньо — на флешці).

Перевірено в контейнері на тестовому потоці: сегменти пишуться (з
07.10.2026 — mkv з `h264` і `pcm_alaw`), запис бере 0,3 % CPU, повне
прибирання й відновлення після зникнення джерела працюють. RTSP зі
справжньої C100 — на точці.

### Вивантаження

Раз на годину recorder із JWT точки бере в `api` **тимчасовий ключ R2**
(Cloudflare temp-access-credentials: лише префікс `<point>/`, TTL 1 година,
`services.md` §3). Раз на хвилину: беремо всі файли, старші за 70 секунд
(щоб не чіпати той, у який ffmpeg зараз пише), робимо S3 `PUT` з цим ключем,
після підтвердження — видаляємо локально й реєструємо сегмент в `api`.
Реєстрація, що не пройшла, досилається окремим проходом **без повторного
завантаження**: ключ у R2 детермінований, а перезаписати обʼєкт під bucket
lock однаково не можна. Якщо відповідь на `PUT` загубилась, `HEAD` з тим
самим розміром — це успіх, а не привід вантажити знову.

**Чому тимчасовий ключ через наш API, а не постійний ключ чи presigned на
кожен файл.** Постійний ключ R2 на пристрої в публічному коридорі — це
доступ до всього бакета. Presigned URL на кожен сегмент безпечніший, але
кожне вивантаження тоді залежить від `api`: ліг `api` на пів години — лягло
вивантаження. Тимчасовий ключ живе годину, тож короткий обрив бекенду
recorder переживає, а в чужих руках ключ обмежений префіксом точки й
годиною. Права «лише запис» R2 не має, тож від видалення й перезапису
захищає не ключ, а bucket lock (нижче). Відкликати все одразу —
відкликати батьківський токен у Cloudflare.

**Як зроблено насправді (06.10.2026) — підписане посилання на кожен
сегмент, а не тимчасовий ключ.** Причина на самій малині: `curl` 7.52 на
Stretch не вміє підписувати S3-запити (`--aws-sigv4` з'явився в 7.75), а
рахувати SigV4 у shell на Pi 1 для кожного файла — крихко. Плата, про яку
йдеться вище, — залежність від `api` — виявилась дешевою: флешка однаково
тримає дні запису, тож ліг `api` — вивантаження просто чекає, а ключа від
бакета на пристрої немає зовсім. Компонент — `uploader` стеку: з 15.10.2026
це `bin/uploader` (C, `raspberry/kiosk/src/uploader/uploader.c`), у який
`exec`-ає `raspberry/pi/stack/uploader.sh`; той самий скрипт і далі вміє все
сам (`UPLOADER_IMPL=sh` у `config/env` — відкат без релізу). Працює поруч
із recorder:

1. Готові сегменти — ті, що не мінялись понад хвилину (у свіжий ще
   пише ffmpeg), найстаріші першими, до 20 за прохід. З 15.10.2026 спершу
   з RAM (усі, крім того, в який пише ffmpeg; див. «Спершу в RAM» вище), а
   хвіст із флешки — лише поки в RAM не з'явився новий готовий.
2. `POST /points/:id/video/upload` (ключ точки) → ключ
   `<точка>/<камера>/<UTC-дата>/<ім'я>` і підписаний `PUT` на годину.
   Ключ детермінований: повтор після обриву перезаливає той самий об'єкт.
3. `curl -4 -T` прямо в R2, байт-у-байт, з **адаптивною стелею** й порогом
   `--speed-limit 2000 --speed-time 30`: якщо віддача падає нижче 2 КБ/с на
   30 с — обрив (не висіння до `--max-time`), бо відео — найнижчий пріоритет
   і не має тримати аплінк, по якому ходять платіжний термінал, тунель і
   телеметрія (власник, 09.10 і 12.10.2026). `nice`/`ionice` знижують
   пріоритет лише на процесорі й диску, мережа їх не бачить, і фіксовані
   400 КБ/с на каналі в 10 КБ/с були всім каналом. Тому дані в curl подає
   сам аплоудер (колбек читання в C, `pace()` у скрипті): по «секунді»
   темпу за раз, а темп підлаштовується
   щодві секунди **прямо під час файла** — пінг до api понад базу на 400 мс
   або загубився **два рази поспіль**, чи curl не встигає забрати шматок →
   ×0,8; тихо (до +150 мс) → ×1,25; межі 32…800 КБ/с. Так з 15.10.2026:
   доти гальмувало ×0,6 від одного пінгу на +150 мс, і на Wi-Fi клубу, де
   затримка гуляє й без нас, темп сидів на 10–50 КБ/с при записі ~80 КБ/с —
   черга росла на гігабайти за добу. Регулятор однаковий для всіх точок,
   крутиться через `config/env`: `UPLOAD_RTT_SLACK_MS` (400),
   `UPLOAD_RTT_QUIET_MS` (150), `UPLOAD_BACKOFF_PCT` (80),
   `UPLOAD_BAD_SAMPLES` (2), `UPLOAD_MIN_KB` (32), `UPLOAD_RATE` (800k),
   `UPLOAD_MAX_PAUSE_S` (120 — пауза після збоїв);
   старий, обережний — 150 / 60 / 60 / 1 / 8. Стеля між файлами
   піднімалась би годинами: на 8 КБ/с один сегмент іде 12 хвилин. Темп і
   останній замір лежать у
   `state/` (`upload.cap`, `upload.last`) і переживають ребут, а телеметрія
   щохвилини відправляє замір: `upload_kb_s`, `upload_ok`, `upload_at`,
   `upload_limit_kb_s` (в адмінці — «Мережа точки» й «Компоненти точки»),
   а з 14.10.2026 ще й черга: `upload_queue` (скільки сегментів чекає) і
   `upload_oldest` (коли записаний найстаріший) — рядок під графіком
   заливки. **Битий сегмент чергу не тримає** (14.10.2026): порожній файл,
   ім'я без часу чи 400 від api (`bad_bytes`, `bad_started_at`…) — і файл
   їде в `rejected/` поруч із буфером з причиною в лозі, а аплоудер бере
   наступний. Досі такий файл повертав помилку щоразу, аплоудер на кожну
   ставав на паузу до 10 хв і починав з нього ж, найстарішого, — заливка
   стояла годинами, а в телеметрії не було навіть невдалих замірів (збій до
   самої заливки замір не пише). На 401/403/429 і обриви файли лишаються в
   черзі: відкликаний ключ не має перенести в `rejected/` усе підряд.
   **409 від R2** — окремий випадок, і саме він зупинив чергу 14.10.2026 на
   дев'ять годин: заливка дійшла до кінця, реєстрацію обірвав перезапуск
   аплоудера, а повторна заливка того самого ключа впирається в bucket lock
   (перезаписувати не можна тиждень). Тепер на 409 аплоудер просить api
   зареєструвати вже наявний об'єкт (api звіряє розмір HEAD-ом): збігся —
   локальну копію прибирає, ні (`size_mismatch`) — файл у `rejected/`.
   Межа 800 КБ/с ≈ 8 потоків 720p (~95 КБ/с; до 12.10.2026 була 400): година накопиченого
   доганяється за ~8 хвилин. Довжину файла curl отримує заголовком і без
   chunked (`Transfer-Encoding:` порожній): R2 chunked не приймає, а curl
   7.52 зі Stretch шле його з `-T -` навіть поруч із `Content-Length`.
   IPv4 — бо IPv6 до R2 на 4G точки зламаний. **Була межа заліза:** 1080p — це ~1,2 Мбіт/с, а 4G на
   віддачу стільки стабільно не тягне, тож буфер ріс, а аплоудер майже
   завжди активний. Лікування — `stream1` на 720p замість 1080p
   (09.10.2026, через ONVIF — `scripts/camera-onvif.mjs`, нижче
   «Роздільність»): менше пікселів → менший реальний бітрейт
   (~0,75 Мбіт/с, сегмент ~5,7 МБ/хв замість ~9), і аплоудер наздоганяє
   канал. Відео лишається best-effort і терміналу не заважає.
4. `POST /points/:id/video/segment` — api сам робить `HEAD` в R2 і
   реєструє сегмент у `video_segments` лише тоді, коли об'єкт є й має той
   самий розмір. Тільки після цього локальна копія стирається.
5. Збій — пауза від 30 с до 2 хв (`UPLOAD_MAX_PAUSE_S`; до 15.10.2026 — до 10 хв: після обриву на пів хвилини заливка стояла по 5–10), без однакових рядків у лозі.

**Чому аплоудер на C (15.10.2026).** На Pi 1 скрипт коштував процесора
більше, ніж сама заливка. Кожна HTTPS-розмова через `curl` — це новий
процес і нове TLS-рукостискання, ~0,95 с CPU (заміряно: ~0,25 с — старт
curl і розбір CA, ~0,7 с — рукостискання), а на сегмент їх три (посилання,
заливка, реєстрація). Зверху `pace()` щосекунди запускав `dd` і `sleep`,
а щодві — `ping` з `sed`: усе разом — сотні процесів на хвилину, і
процесор точки сидів на 100 %. `bin/uploader` робить те саме одним
процесом: ті самі рішення, файли стану й рядки в лозі, тож телеметрія й
адмінка різниці не бачать. Два зʼєднання — до api й до R2 — живуть між
сегментами в кеші libcurl. Рядок «…, нове зʼєднання» в лозі означає, що
для цієї заливки TLS довелось піднімати заново; у штатному ритмі його
бути не повинно. Пінг регулятора — це час TCP-з'єднання з api (SYN →
SYN/ACK; закриваємо RST-ом, без TIME_WAIT), бо ICMP без root не
відправиш, а `ping` як процес — саме те, від чого тікали. Збирається тим
самим `make pi`, їде в релізі поруч із `bin/kiosk`; `kiosk_sig` апдейтера
бере лише `bin/kiosk` і `assets/`, тож нова версія аплоудера кіоск не
перезапускає, а супервізор перезапускає компонент і тоді, коли змінився
лише `bin/uploader` (`same_code`). Перевірено на моку api/R2: усі
сценарії скрипта, ARM-збірка під QEMU з тим самим libcurl 7.52, регулятор
на каналі зі справжнім зворотним тиском TCP (~58 КБ/с) і SIGTERM посеред
заливки (вихід < 1 с, файл лишається в черзі).

Імена сегментів з 06.10.2026 — в UTC із `Z` (`20261007T171019Z.mkv`; до
07.10.2026 — `.ts`): місцевий час на переході на літній дає дві однакові
години. Час початку uploader шле числом, тож старі імена в місцевому часі
теж розбираються правильно. `content-type` підписаного `PUT` — за
розширенням (`video/x-matroska` чи `video/mp2t`). В адмінці («Відео» →
«Записи») — список і дві кнопки: «дивитися» відкриває плеєр у попапі,
«завантажити» віддає файл (підписаний `GET` на 10 хвилин, з attachment). І
там, і там браузер бере відео прямо з R2 — api лише підписує посилання й
сам жодного байта не пропускає. mkv (H.264 + звук A-law) Chromium програє
разом зі звуком (перевірено 12.10.2026); три перші сегменти в TS від 06.10 і
будь-що в Safari — ні, для них плеєр так і каже й лишається VLC. Посилання
плеєра живе годину: він докачує файл шматками, поки перемотують. Бакет `extrovert-video` уже має lifecycle
`expire-30d` (з 15.10.2026, тимчасово; до того — `expire-7d`, таблиця «R2» нижче).

**Пауза заливки** (17.10.2026). На сторінці точки в адмінці — «⏸ пауза
заливки»: `points.video_upload_paused_at`, і на запит посилання
(`video/upload`) api відповідає `423 upload_paused`. Саме 423, а не 400: на
400 uploader відкладає сегмент у `rejected/` як битий, а на решту кодів лишає
його в черзі й перепитує з відступом до `UPLOAD_MAX_PAUSE_S` (2 хв) — тобто
на паузі малина шле один дрібний запит раз на дві хвилини. Запис іде далі,
сегменти лягають на флешку (при ~80–150 КБ/с потоку це 7–13 ГБ на добу, а
флешка на точці — 29 ГБ), а за дві хвилини після зняття паузи малина
доганяє чергу сама. Пауза діє, щойно малина вийде в мережу, і релізу не
потребує. Навіщо була перша: перевірити, чи малина 16.10 падала від
навантаження на живлення (raspberry-pi.md, «Помилки ядра в телеметрії»).

**Скільки насправді** (C100 kyiv-01): `stream1` за замовчуванням віддавав
1920×1080 незалежно від якості в застосунку Tapo, ~1,34 Мбіт/с — сегмент
~10 МБ на хвилину, ~14 ГБ на добу. З 09.10.2026 `stream1` переведено на
1280×720 (ONVIF): ~0,75 Мбіт/с, сегмент ~5,7 МБ/хв, ~8 ГБ на добу. На
Pi 1 запис бере ~18 % CPU (не 4 %, як з емулятора: весь потік іде USB-шиною,
спільною для мережі й флешки), кіоск просідає з ~48 до ~43 fps, температура
росте до ~77 °C.

Роздільність `stream1` міняється **через ONVIF, не в застосунку Tapo** —
той головний потік не чіпає (віддає 1080p за будь-якої «якості»). З хоста:
`bash scripts/pi-forward.sh kyiv-01 47620 192.168.199.243:2020` прокидає
ONVIF-порт камери (2020) через тунель малини, далі
`bun scripts/camera-onvif.mjs localhost:47620` показує профілі й дозволені
роздільності, а `… localhost:47620 1280x720` виставляє. SOAP-запити дрібні,
аплінк не вантажать. Застереження: C100 через ONVIF приймає лише
роздільність — стелю бітрейту (`BitrateLimit`) і «якість» ігнорує, тож
реальний бітрейт опускає сам перехід на менше пікселів. `ForcePersistence`
тримає налаштування через перезавантаження камери.

Буфер: 8,2 ГБ на добу, тож USB-носій на 64 ГБ = **тиждень автономності**. Карта в
камері на 16 ГБ (48 годин) лишається як третій рівень — на випадок, коли здох
сам edge-вузол. Дістати з неї запис можна тільки руками через додаток Tapo:
ONVIF у C100 має лише Profile S, автоматичного дозаливання прогалин не існує.

## R2

Два бакети з чотирьох (повний перелік і розмежування оточень —
`services.md` §2.1), бо в них різна доля:

| Бакет | Що | Lifecycle | Bucket lock |
|---|---|---|---|
| `extrovert-video` | сирі сегменти | **видалення через 30 днів** (з 15.10.2026, тимчасово: поки аналізатор не доведений, записи потрібні для перевірки; потім — назад до 7) | 7 днів: ні видалити, ні перезаписати, навіть із ключем пристрою |
| `extrovert-evidence` | аркуші-докази подій (з 12.10.2026 — усіх, див. «Воркер»), смужки вирізок людей (з 15.10.2026), за потреби кліпи | **без обмеження** — вирізки й докази зберігаються безстроково (власник, 15.10.2026): аркуш ~100–140 КБ, смужка проходу ~60 КБ, тобто ~50–80 МБ на добу на точку | не потрібен |

Lock не довший за lifecycle: інакше lifecycle не зможе видалити сегмент,
і бакет ростиме. Bucket locks в R2 є з березня 2025 — це те, що дає
видавати пристроям ключ із правом запису й не боятися за архів.

Ключі — за схемою з `urls.md`, ідентифікатор точки першим сегментом:

```
extrovert-video/<point>/<camera>/2026-10-07/20261007T142300Z.mkv      запис малини
extrovert-video/<point>/<camera>/2026-10-10/sd-20261010T194723Z.mkv   архів картки камери
extrovert-evidence/<point>/<event_id>/sheet.jpg                       аркуш події (з 15.10.2026)
extrovert-evidence/<point>/<event_id>/{frame_00.jpg,clip.mp4}         кадр і кліп (до 15.10.2026)
extrovert-evidence/<point>/p/<passage_id>-<segment_id>.jpg            вирізки людини з проходу
```

Година в ключі — щоб префіксний листинг за період був дешевим. Ключі доказів
воркер ще й записує в `video_events.evidence` і `video_passages.crops`: бакет
приватний, і адмінці потрібні точні імена, щоб видати підписане посилання,
не лістячи префікс.

Бакети створювати з **EU jurisdiction**, щоб дані не роз'їжджались за межі ЄС.

> ⚠️ **Пастка.** Lifecycle видаляє за розкладом і не питає, чи ми встигли
> обробити. Якщо воркер відстане на тиждень — відео зникне мовчки. Тому в
> `overseer` додається перевірка: вік найстарішого необробленого сегмента
> більший за 3 доби → повідомлення в чат. Це головний алерт усієї підсистеми.

## База

Постгрес на старті лишається там, де він і зараз — **у докері на `public`**,
поруч із рештою стека. Керована база DO коштує $15,15/міс і на цій стадії
купує рівно одне: щоб нам не довелося думати про бекапи. Тож про них треба
подумати самим, і зробити це нормально.

Відео в базі не зберігається ніколи — тільки ключі й метадані.

### Бекапи в R2

Два рівні, бо вони рятують від різного:

| Рівень | Чим | Як часто | Від чого рятує |
|---|---|---|---|
| Фізичний | WAL-G (або pgBackRest) → бакет `extrovert-backup` | базовий раз на тиждень + WAL безперервно | смерть диска, дроплета, датацентру. RPO — хвилини, є PITR |
| Логічний | `pg_dump -Fc` → той самий бакет | раз на тиждень | зіпсована міграція, випадковий `DELETE`, переїзд на іншу версію PG |

Логічний потрібен саме тому, що фізичний бекап **бездоганно реплікує помилку**:
якщо міграція знесла таблицю, вона знесена і в усіх WAL. Дамп дає точку, з якої
можна дістати дані руками.

Обидва — S3-сумісним клієнтом у R2 (`endpoint`, `provider = Cloudflare`).
Окремий бакет і **окремий токен**, не той, яким користується заливка відео.

> ⚠️ **Від зламаного `public` бекапи захищає bucket lock.** Токен із
> дроплета міг би видалити бекапи, тому на `extrovert-backup` стоїть lock
> довший за цикл повного бекапу (наприклад, 35 днів). Lock не рятує, якщо
> зламано сам акаунт Cloudflare, тож раз на місяць — ще й копія дампа за межі
> периметра: локальний диск, домашній NAS, будь-що поза DO і поза Cloudflare.

**Бекап, який жодного разу не відновлювали, — це не бекап.** Раз на квартал
розгортаємо останній дамп на дроплеті `analysis`: він приватний, майже не
навантажений і вільний саме для такого. Звіряємо кілька лічильників (кількість
чеків, сума балансів) — і тільки після цього вважаємо, що бекап є.

Обсяг невеликий: `video_events` — порядку тисячі подій на добу на точку по
пів кілобайта, `video_passages` — стільки ж проходів по ~4 КБ (вектор
зовнішності 768 чисел і стиснутий трек), тобто кілька мегабайтів на добу.
Бекапи в R2 коштуватимуть центи.

### Що ми свідомо приймаємо на себе

Дроплет із базою стає єдиною точкою відмови. Померла файлова система — база
піднімається з R2 руками, RTO — десятки хвилин, і всі точки в цей час не
приймають замовлення. За $15/міс керована база це знімає. Переїжджати варто,
коли спрацює хоч одне:

1. Півгодинний простій уже коштує дорожче за $15.
2. База переросла кілька гігабайт і `pg_dump` перестав встигати між ніччю.
3. Зʼявилась людина, якій потрібен доступ до бази, але не потрібен SSH на сервер.

### Схема

Повна схема — `db/schema.sql`, ER-діаграма й колонки — `db-schema.md`. Що
де лежить:

| Таблиця | Що | Хто пише |
|---|---|---|
| `video_segments` | сегменти запису: журнал і черга обробки водночас. `source` — `pi` (малина пише безперервно) чи `sd` (архів картки камери, лише рух); `analysis_version` — якою версією аналізу оброблено | api (реєстрація заливки малини), імпорт картки, worker (статус) |
| `video_coverage` | коли камера працювала, для архіву картки: від першого до останнього кадру кожного файлу. Для малини покриття — самі сегменти | імпорт картки |
| `video_passages` | прохід людини коридором: трек, напрямок (`direction`, `heading`), чи стояла біля кавʼярні й біля автомата, вирізки (`crops`), вектор зовнішності (`embedding`), людина (`person_id`), чек (`receipt_id`, `receipt_match`) | worker |
| `video_events` | події для адмінки: `approach`, `machine`, `pass`, `queue`; `passage_id` — прохід людини, `likely_receipt_id` — чек, `superseded_at` — замінена переаналізом | worker |
| `video_people` | людина — кластер проходів за одягом, не довший за 18 год; `staff` — персонал | worker (people.py), перераховує останню добу щоразу заново |
| `video_visits` | візит людини від входу в зал до виходу (кінці можуть бути невідомі) | worker (people.py) |

`meta` подій — JSONB, розмір не обмежений схемою: тривалість, впевненість
моделі, напрямок проходу. GIN-індекс дає пошук за вмістом без міграцій.

### Черга

Перша схема архітектури обходилась без черги завдань: вистачало Redis
pub/sub. Для відео цього **не вистачає**: pub/sub втрачає повідомлення при перезапуску
підписника, а втрачений сегмент — це діра в архіві, яку ніхто не помітить.
Тому черга тут — та сама таблиця, через `SKIP LOCKED` (`worker/db.py`):

```sql
update video_segments s
   set status='processing', locked_at=now(), attempts=attempts+1
 where s.id = (
   select id from video_segments
    where status='pending'
       or (status='processing' and locked_at < now() - interval '15 minutes')
       or (status='failed' and attempts < 5)
    order by source = 'sd', started_at       -- малина першою, архів картки потім
    limit 1
    for update skip locked)
returning *;
```

Запис малини йде першим: архів картки доливається пачкою на сотні сегментів,
і без цього свіжі хвилини чекали б годинами. Усередині джерела — за часом:
прохід, що впирається в початок сегмента, дошивається до проходу
попереднього, тож попередній мусить бути вже оброблений.

**Переаналіз.** Коли черга порожня, воркер бере найстаріший `done`-сегмент
з `analysis_version` меншою за поточну (`config.ANALYSIS_VERSION`, зараз 2) і
переробляє його. Старі події сегмента не видаляються, а позначаються
`superseded_at`: на них може посилатись `redemptions.evidence_event_id`, і
доказ, яким колись підтвердили бонус, мусить лишитись. Усі запити адмінки
беруть лише `superseded_at is null`. Старі проходи сегмента видаляються —
на них ніхто ззовні не посилається. Усе, що воркер пише про сегмент
(проходи, події, чеки, статус `done`), — одна транзакція: впав посередині —
сегмент лишився `processing`, і через 15 хв його підбере знову без половинок.
Вимкнути переаналіз — `REPROCESS=0`.

Окрема сутність (Redis Streams, RabbitMQ, Kafka) на наших обсягах — зайва
залежність, яку доведеться доглядати. Redis лишається на `public` для того, для
чого він і був: pub/sub подій, сесії, rate limit.

## Воркер

Цикл: взяти сегмент → викачати з R2 → продетектити → проходи людей → події
→ записати разом із чеками й `done` → вивантажити докази. Між сегментами —
люди й візити (`people.py`) і чеки, що доїхали пізніше.

**Головний важіль вартості — скільки кадрів іде через модель.** Рахунок нижче
з 80 мс на кадр (YOLO-n, ONNX, одне ядро shared-vCPU) і повного декоду доби
відео за ~1,2 ядро-години:

| Режим | Кадрів через модель на добу | Ядро-годин на добу |
|---|---|---|
| Усі 15 fps | 1 300 000 | **~30** |
| Семплінг 2 fps | 173 000 | ~5 |
| 2 fps + гейт по руху | ~20 000 | **менше 1** |

У добі всього 24 ядро-години, тож **повні 15 fps не влазять в одне ядро навіть
для однієї камери** — і це головна причина не робити «просто обробимо все».

За замовчуванням — **2 fps і гейт по руху**: перший прохід лише по ключових
кадрах (їх ~0,4 на секунду), і тільки сегменти, де щось ворушилось, ідуть на
повний декод і в модель. Повний архів при цьому лишається повним. У такому
режимі одна камера вантажить ядро на одиниці відсотків, а весь інший запас іде
на наздоганяння черги після обривів звʼязку.

```bash
# перший прохід — тільки ключові кадри, дешево
ffmpeg -skip_frame nokey -i seg.mkv -vsync 0 -f rawvideo -pix_fmt rgb24 -

# другий — повний декод із семплінгом, лише для «цікавих» сегментів
ffmpeg -i seg.mkv -vf fps=2 -f rawvideo -pix_fmt rgb24 -
```

Реалізація — `backend/worker/` (з 23.09.2026, проходи й люди — з
15.10.2026): черга через `SKIP LOCKED`, обидва проходи ffmpeg, yolo11n в ONNX,
проходи, події, впізнавання за одягом і звірка з чеками. Що там заміряно —
у `backend/worker/README.md`.

**Знаменник конверсії — люди, а не порожні хвилини.** До 12.10.2026
знаменником був `idle` — рядок на кожен період, коли біля стійки нікого;
порожнечу складувати сенсу немає, і старі `idle` прибрала міграція
`20261012100000`. Потім конверсією була `approach / (approach + pass)` — але
подія — це прохід, а не людина: гість, що за вечір тричі пройшов коридором
повз кавʼярню, давав три `pass`. З 15.10.2026 воронка в адмінці («Відео» →
«Аналітика») — **унікальні люди**: у кадрі → біля кавʼярні від 4 с → впритул
до автомата → купили (чек у мить, коли стояли біля автомата), без
персоналу. Події лишаються як були: одна людина за прохід — `approach` або
`pass`, а `machine` — додатково до `approach`.

### Конвеєр сегмента (15.10.2026)

```
ffmpeg: 2 кадри/с, 1280×720 ──► кадр детектора 640×360 (середнє 2×2)
                                 │
                YOLO-n ──► треки ──► вирізки людей з повного кадру
                                 │
                    проходи (треки, зшиті через розриви, без маски сцени)
                        │                         │
           напрямок, зона, автомат        8 вирізок ──► вектор (3 моделі Intel)
                        │
        події approach | machine | pass | queue + аркуші-докази
```

Декодуємо вдвічі ширше, ніж бачить модель: модель отримує ті самі 640×360,
що й раніше, а вирізки людей беруться з 1280×720 — для впізнавання за одягом
пікселі потрібні (на 640 людина в глибині коридору — 40 пікселів заввишки).
Кадр зменшується в PIL (`Image.reduce`), а не numpy: reshape із сумою по осях
брав 96 мс на кадр — більше, ніж сама модель. На пів ядра найзавантаженіша
хвилина (покупка з чергою, 10.10 22:47) обробляється за 38 с, тобто 1,6×
реального часу, пік памʼяті контейнера — 431 МБ при стелі 600.

**Прохід** (`passages.py`) — людина від появи в кадрі до зникнення. Трекер
рве людину, коли детектор губить її довше ніж на 1,5 с (перекрила інша,
пройшла під самою камерою), тож трек, що почався до 4 с після кінця іншого
там само (ноги ближче 0,18 кадру) і не надто несхожий на нього (вектор
≥ 0,30), — продовження того самого проходу. На архіві картки без цього одна
людина давала два-три `pass`. Прохід, що впирається в край сегмента,
дошивається до проходу сусіднього сегмента тими самими порогами
(`db.write_passages`).

**Напрямок** — звідки й куди змістились ноги (низ рамки; під камерою, де
ноги вже за кадром, глибину добудовує маківка): `away` (від камери вглиб),
`toward` (до камери), `near`, `far`, `uturn` (з глибини до камери й назад),
`uturn_far`. Що це означає на точці — сцена (`heading`): на kyiv-01 коридор
веде від рецепції під камерою до залу, тож `away` — зайшов у зал, `toward` —
вийшов. Перевірено на архіві: між «від камери» і наступним «до камери» тієї
самої людини медіана 9 хв, верхня чверть — від 70 хв (час у залі), навпаки —
0,7 хв (вийшла до рецепції й повернулась).

**Подія `machine`** — людина впритул до самого автомата, а не просто тупцює
в коридорі біля камери: рамка обрізана низом кадру, її ліва межа (медіана)
не правіше 0,34 кадру, центр зсувається в середньому не більш як на 0,055
кадру за пів секунди, і так щонайменше 4 с. На 36 розмічених кандидатах з
архіву картки правило знайшло всіх 10 справжніх і одного хибного (поліз у
холодильник поруч).

**Доказ — аркуш** (з 15.10.2026): три кадри події — початок, найпевніший
кадр, кінець — з рамками (червона — людина події, у черзі — усі, хто стояв;
жовті — інші в кадрі; блакитна лінія — межа зони) і під ними вирізки цієї
людини з усього проходу. З одного кадру не видно, що людина робила: підійшла
до автомата чи пройшла повз, хто стояв поруч. Кадри беруться з тих, що вже
пройшли через детектор, а не окремим ffmpeg на кожну мить: подій сотні на
добу. Окремо кожен прохід кладе смужку своїх вирізок (до 8, рівно за часом:
і спиною, і обличчям) — `video_passages.crops`, з них можна перерахувати
вектори іншою моделлю, не маючи вже самого відео.

### Сцена точки (`backend/worker/scenes.json`)

Усе, що залежить від того, де саме висить камера, — у сцені, а не в коді:
той самий воркер обробляє відео з будь-якої точки, а сцена береться за
`point_id`/`camera_id` сегмента (ключ `<point>:<camera>`, потім `<point>`,
поверх `default`). Звідки відео — видно з самого сегмента: малина реєструє
його з ідентифікатором своєї точки, імпорт картки — з точкою, з якої картка.

| Поле | Що | kyiv-01 |
|---|---|---|
| `zone` | смуга «біля кавʼярні» в частках кадру (низ рамки) | ≥ 0,93, як усюди (камера на стійках висить однаково) |
| `masks` | прямокутники, де детектор бачить не людей; трек, що 60 %+ точок сидить у масці, — не прохід і не подія | дзеркало з лампочками на стіні VIP-зони в кінці коридору: 11.10 о 09:17 прибиральниця і її відображення — двома рамками; за 4½ доби архіву ~20 хибних `pass` |
| `machine` | де стоять біля автомата (див. `machine` вище); `null` — події немає | під камерою ліворуч від центру |
| `heading` | що означає напрямок: `away`/`toward` → `in`/`out`; `null` — входи й виходи не рахуються | `away` — у зал, `toward` — із залу |



### Зона: «біля кавʼярні» — це впритул (12.10.2026)

Камера висить **на самій кавʼярні** — зі стелі ніші ліворуч від монітора,
обʼєктив на 1745 мм, нахил 15° (`design/mockup`, `CAM`). У кадрі коридор
клубу, і більшість людей у ньому — перехожі. Той, хто справді щось робить із
кавʼярнею або хоча б читає меню, стоїть упритул: низ кадру торкається підлоги
приблизно за 2 м від обʼєктива, тож рамка такої людини **обрізана низом
кадру**. Звідси зона — смуга, де низ рамки ≥ 0,93 висоти кадру
(`zone` у `backend/worker/scenes.json`, однакова для всіх стійок, бо камера на
них висить однаково).

Заміри на 29 сегментах: люди біля кавʼярні стоять у цій смузі 19–62 с,
перехожі, що йдуть повз саму камеру в коридор, — до 2,5 с. Поріг підходу —
**4 с**: півтора запасу над найдовшим перехожим. Чергу рахуємо по тих самих
відрізках, що тягнуть на підхід, — інакше уламок рамки (детектор інколи дає
другу рамку на руку тієї ж людини) роздував чергу.

Перехожий — трек, що жодного разу не тягнув на підхід, від двох кадрів і не
сидить у чужій рамці (`events.is_person`). Уламки рамок — постер на стіні,
рука людини, що вже має свою рамку, — живуть 1–2 кадри й на 30–96 % сидять у
чужій; перехожий біля самої камери проскакує за 2 кадри, але ні з ким не
перетинається. Результат на тих самих 29 хвилинах: 4 підходи, 17
перехожих, 1 черга — підходять ~19 %. Кадри перехожих перевірені очима:
групу з трьох-чотирьох людей лічильник бачить як трьох, а людину, що
підійшла й пішла під новим треком, вдруге не рахує. Чого він не вміє —
впізнати того самого гостя, що пройшов двічі (див. «Ідентифікація людей»).

**Доказ — для кожної події** (рішення власника, 12.10.2026): до 15.10.2026
кадр, тепер аркуш (див. вище) у `extrovert-evidence`. Поки пороги
підкручуємо, очима треба перевіряти саме події без чека. Це знімки людей без
покупки, тож коли якість устоїться, обмеження варто повернути (лише події з
чеком). В адмінці («Відео» → «Події») — «переглянути» в попапі,
«завантажити» й «вирізки» проходу.

## Ідентифікація людей

### Обличчя — ні

Тут свідоме обмеження, і воно не технічне лінивство, а арифметика.

Камера дає **823 px/м на відстані метра**. Міжзінична відстань людини ~63 мм —
це **52 пікселі**. Для моделей типу ArcFace це нижня межа працездатності, і то
за ідеальних умов; ширина обличчя 123 px при вході моделі 112×112, тобто запасу
немає взагалі. На двох метрах — 26 px, тобто нічого. Додати ракурс згори під
15° і збоку під 25°, 15 fps із розмиттям у русі, контрове світло з коридору і
відсутність WDR — і стає видно, що **стабільний ID людини по обличчю з цієї
камери отримати не вийде.**

> **Перевірено 23.09.2026** на чужому CCTV-відео (`tools/reid_lab.py`,
> детектор YuNet і розпізнавач SFace, обидва вбудовані в opencv). Висновок
> підтвердився, але причина інша, ніж тут написано. Пікселі — не головне:
> при ширині обличчя 48 px модель помилково склеює 8 % різних людей, і це
> ще робоча зона. Ламається **ракурс**: на зйомці згори обличчя або не
> знаходиться взагалі (одна детекція на 50 секунд відео), або дає 12–31 px,
> і тоді 65–75 % чужих людей оголошуються тією самою. Числа, таблиці й
> методика — `backend/worker/README.md`.

Якщо колись знадобиться справжнє впізнавання облич — це **інша камера**: на
висоті 1,4–1,5 м, фронтально, 4 МП замість 2. І окремо памʼятати, що шаблон
обличчя — біометричні дані, тобто інша правова категорія, ніж звичайне
відеоспостереження.

### Люди й візити — за одягом, у межах доби (15.10.2026)

Обличчя з цієї камери не впізнати, а **одяг у межах доби — можна**, і саме
це дає відповіді на питання власника: скільки різних людей буває в клубі за
добу, по годинах, і скільки людина в ньому сидить. Перевірено на архіві
картки камери 09–14.10 (4½ доби, 1660 проходів) — локально тим самим кодом,
що й прод-воркер.

**Вектор зовнішності** — три моделі Intel Open Model Zoo,
`person-reidentification-retail-0277/0286/0287` (OpenVINO, разом 17 МБ,
~25 мс на вирізку на модель на одному ядрі), навчені саме на цьому: та сама
людина з різних боків у камерах магазинів. Вектор проходу — для кожної
моделі зважене середнє по 8 вирізках, і три блоки поруч; схожість — середній
косинус трьох моделей. Якість без ручної розмітки (свої пари — половини
одного треку, чужі — треки з різних діб):

| Ознака | спина ↔ спина, AUC | спина ↔ обличчя (вхід ↔ вихід), AUC |
|---|---|---|
| гістограма кольору одягу | 0,80 | 0,84 |
| DINOv2 (загальна модель зору) | 0,58 | 0,80 |
| одна модель Intel 0277 | 0,98 | 0,91 |
| **три моделі Intel разом** | **0,98** | **0,93** |

**Людина** (`worker/people.py`) — кластер проходів, агломеративно із
середнім звʼязком, поріг 0,55: на ручній розмітці 66 пар вище нього 95 % —
справді та сама людина. Жорсткі заборони: два проходи, що були в кадрі
однієї камери одночасно, — різні люди; людина — не довше 18 год (далі одяг
ідентичність не тримає: переодягнувся, інша людина в такій самій чорній
куртці). У впізнавання йдуть лише проходи, що підходили до камери ближче
0,7 кадру й дали хоч дві вирізки: далекий силует у кінці коридору — шум.

Клуб цілодобовий, тож **межі доби немає**: гість, що прийшов о 23:00 і пішов
о 03:00, — одна людина й один візит. Замість доби — ковзне вікно 26 год, що
закінчується зараз: кожен перерахунок (раз на 10 хв, коли є нові проходи)
переписує людей, що зʼявились у вікні, з нуля; людей, що почались раніше й
тривають у вікно, бере «насінням» — їхні старі проходи лишаються з ними, а
нові можуть до них доєднатись. Тому `video_people.id` — не стабільний ключ,
а номер у поточному розкладі. Історію (переаналіз, імпорт картки) воркер
наздоганяє кроками по 20 год.

**Персонал** — людина з 12+ проходами (адміністратор проходить коридором
50–80 разів за зміну, гість — 2–6); схожі на неї дрібні кластери (середня
схожість ≥ 0,45) — теж персонал: проходи впритул до камери чи в натовпі до
порогу не дотягують. Персонал з відвідувачів і воронки виключається.

**Добирання половинок.** Вхід у зал — це спина, вихід — обличчя, і схожість
між ними нижча, ніж між двома спинами, тож кластеризація лишає багато
половинок «зайшов і не вийшов» / «вийшов, не зайшовши». Їх зводимо нижчим
порогом 0,44 (на перевірених парах вище нього 5 з 5 правильні, нижче — 6 з 6
хибні), кожну щонайбільше в одну пару, вихід — від 5 хв після входу.

**Візит** — від входу (`heading = in`) до виходу (`out`); `uturn` (з глибини
до камери й назад) — вийшла до рецепції й повернулась. Перерва до 45 хв
(перекур, по їжу) візит не рве. Будь-який кінець може бути невідомим: вхід
був до початку запису, вихід припав на блекаут, або впізнавання не звело
спину з обличчям.

**Що вийшло на архіві 09–14.10** (офлайн-звіт `video-archive/analysis`,
поза git): відвідувачів за добу — субота 127 (96–148 залежно від порогу),
неділя 109 (88–133), понеділок 91 (76–104); пік — 17–18 год, ~24 людини в
клубі одночасно; медіана часу в клубі ~1 год 12 хв (з 28 візитів, де видно і
вхід, і вихід), середнє 1 год 31 хв. Це оцінка, а не лічильник на дверях:
межі в дужках — розкид від порогу схожості.

**Чого не робимо в проді:** впізнавання між різними добами (той самий
постійний гість у понеділок і в середу) — одяг між днями міняється, і на
архіві це давало лише нижню межу (~20 % людей бачили в інший день); і
розпізнавання мови з аудіодоріжки — з усього звуку архіву
корисного вийшло три епізоди.

### Покупці

Чек — одна мить (`receipts.fiscal_date`), і питання «хто стояв біля
автомата в цю мить» коректне, а «який чек дістався підходу» — ні. До
15.10.2026 чек діставався підходу за часовим вікном (−15 с від початку, +30 с
після кінця, найближчий до «початок + 10 с»), і на архіві картки це вгадало
3 з 4 покупців — раз сусіда, що стояв поруч довше. Тепер покупець — прохід,
рамка якого в мить оплати (±2,6 с) стоїть там, де стоять біля самого
автомата (сцена, `machine`); немає такого — будь-хто в зоні біля кавʼярні.
Один такий — `video_passages.receipt_match = 'alone'`; кілька — `ambiguous`, і
чек дістається тому, хто простояв там найдовше. Чек переходить і на подію
`approach` (або `machine`) цього проходу — `video_events.likely_receipt_id`,
як і раніше. Сусід на стільці поруч (10.10 о 22:47, чек 980) у зоні стоїть, а
біля автомата — ні, тож покупцем уже не стає.

Чек, що доїхав у базу пізніше за свій сегмент (Checkbox poll), воркер
наздоганяє між сегментами — за останні 6 год.

**Три миті покупки** в адмінці («Відео» → «Покупці»): вибір напою — час у
номері замовлення машини (`machine_orders.order_no`: `2026101016171720…` →
16:17:17 за Києвом), оплата — чек, напій готовий — `purchased_at`
замовлення. Замовлення шукаємо за ціною в межах трьох хвилин від чека.

**Невдалі спроби** — подія `machine` від 20 с, а чека в межах [початок −
30 с, кінець + 60 с] немає. Поруч — телеметрія малини в ці хвилини (втрати й
пінг, Wi-Fi чи LTE) і чи кавомашина була на звʼязку: 14.10 о 23:36 саме так
платіж не пройшов — LTE губив 16–28 % пакетів, а термінал оплати ходить через
той самий 4G-роутер і запасного каналу не має.

### Архів картки камери

Камера (Tapo C100) пише на свою microSD лише фрагменти з рухом, склеєні у
файли по 256 МБ, і справжнього часу в mp4 немає — лише годинник на кадрі.
Коли малина не писала (09–14.10.2026), архів картки доливається в прод
тими самими сегментами, що й запис малини, і прод-воркер аналізує його тим
самим кодом:

1. Годинник читається з кожного кадру (шаблонне розпізнавання цифр OSD), і
   файл ділиться на ділянки зі сталим зсувом «час на стіні − позиція у
   файлі»: усередині фрагмента з рухом зсув сталий, між фрагментами стрибає.
2. З ділянок вирізається все, що вже є в проді від малини (дублікатів бути
   не має), решта ріжеться на шматки до 60 с і **перекодовується** (H.264,
   1280×720, звук як є): копія без перекодування ріже лише по ключових
   кадрах, і час першого кадру поїхав би.
3. Шматки — у `extrovert-video` під `<point>/<camera>/<дата>/sd-<час>Z.mkv`,
   рядки — у `video_segments` (`source = 'sd'`, `pending`), а проміжки, коли
   камера працювала (від першого до останнього кадру кожного файлу), — у
   `video_coverage`: пауза між фрагментами картки — це або порожній коридор,
   або вимкнена камера, і без покриття години без запису виглядали б як
   години без людей.

Файли без годинника на кадрі (09.10 19:44 → 10.10 10:48 OSD був вимкнений)
не імпортуються: час кадру там лише приблизний, а прод рахує людей і чеки по
секундах. Скрипти — `video-archive/analysis/code/sd_import.py` (поза git,
разом з розпізнаванням годинника): `plan` → `cut` → `upload` → `register`.

## Скільки це коштує

Розрахунок на камеру: **341 МБ/год** (з офіційної таблиці TP-Link, 16 ГБ = 48 год).

| Стаття | Обсяг | На місяць |
|---|---|---|
| R2, 7 діб на камеру | 8,2 ГБ/добу → 57 ГБ | **$0,86** |
| R2 операції запису | 43 тис. PUT/міс на камеру | $0 (безкоштовний мільйон ≈ 23 камери) |
| R2 egress | скільки завгодно | **$0** |
| R2 бекапи бази | менше 1 ГБ | ~$0,02 |
| Дроплет `public` 2 vCPU / 4 ГБ | 80 ГБ SSD, база в докері | $24,00 |
| Дроплет `analysis` 1 vCPU / 2 ГБ | 50 ГБ SSD | $12,00 |
| **Разом на старті (2 точки)** | | **≈ $38** |

Кожна наступна точка додає до хмари **менше долара на місяць**. Разово на
точку — edge-вузол і SSD.

Саме нульовий egress R2 робить схему такою дешевою: воркер викачує кожен
сегмент назад, і на S3 чи DO Spaces цей трафік коштував би більше за саме
зберігання.

## Чого свідомо не робимо

- **Розпізнавання облич** — див. розділ вище, пікселів не вистачає
- **GPU** — з семплінгом 2 fps CPU вистачає надовго; GPU-дроплети DO для цього
  абсурдно дорогі
- **Frigate / повноцінний NVR на точці** — воркер у хмарі робить те саме, але
  без залізяки, яку доведеться обслуговувати на кожній точці
- **Tapo Care** — платна хмара TP-Link. Крім того, одночасно можна тримати лише
  дві опції з трьох: Tapo Care, SD, ONVIF/NVR. Ми беремо SD + ONVIF
- **Керована база DO** ($15,15/міс) — поки що постгрес у докері плюс бекапи в
  R2. Умови переїзду перелічені в розділі «База»; це питання «коли», а не «чи»
- **Кластер, Kafka, окремий брокер** — на цих обсягах це самообман
