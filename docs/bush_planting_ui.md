# UI посадки кавенятка — геометрія, зони, слайдери

*Дописано 19.09.2026.* Технічна специфікація екранів посадки (листя,
гілки, бутони) — **зони/криві, формули позиціювання, ліміти кількості,
слайдери, доступні гравцю**. Побудована на робочому прототипі
`design/sprites/tools/planting_points_editor.html` (Крок 3.2 — авторинг
зон/кривих по реальному референс-дереву, Крок 4 — процедурна генерація
10 варіантів для перевірки) і використовує ТІ САМІ формули, що й
production-рендерер (`buildBaseComposite`). Усі числа нижче не з
повітря — вони каліброві по реальних координатах референсного дерева
(`design/sprites/generated/_review/tree_layout.json`) і перевірені
статистично (500 прогонів генератора).

**Цей док НЕ дублює:**
- стадії росту, витрату препаратів, попапи, заморозку на маркеті — це
  `gamification_ui.md` §"Ріст і редагування кавенятка" (без змін);
- каталог скінів, стани настрою, анімації квітів/бобів по стадіях 8-10 —
  це `bush_graphics_customization.md` §3-§10 (без змін).

**Цей док ЗАМІНЮЄ** геометрію зон і бутонної прив'язки з
`bush_graphics_customization.md` §1-§3 (4 прямокутні зони листя,
10-16 сумарно) — те саме розходження описане в §12 нижче, разом із
тим, що саме мало змінитись у двох старих доках.

## 1. Типи елементів і реальний порядок посадки

Чотири типи елементів: **гілка** (`branch`), **листя фону** (`leafBg`),
**листя переднього плану** (`leafFg`), **бутон** (`bud`).

Порядок посадки — за таблицею стадій `gamification_ui.md` (без змін):
переходи 0→1 полив, **1→2 листя**, **2→3 гілки**, **3→4...6→7 бутони**
(по 1, 2, 2, 2). Тобто листя садяться ДО гілок — і, відповідно, до
самого моменту посадки гілок частина геометрії бутонів (гілкові криві)
ще не існує; це не проблема, бо перший бутон садиться лише на переході
3→4, коли гілки вже точно є.

**Листя тепер — це ДВІ ФАЗИ в межах ОДНОГО переходу 1→2** (новий момент,
детальніше §3):

1. Фаза A — **фон** (`leafBg`), обов'язкова, 20-40 листків.
2. Фаза B — **передній план** (`leafFg`), відкривається автоматично
   одразу після підтвердження фази A (кнопка "Далі"), необов'язкова,
   0-5 листків.
3. Один фінальний "Посадити" фіксує ОБИДВІ фази разом одним запитом і
   одним списанням компосту — той самий принцип "чернетка до підтвердження",
   що й у `gamification_ui.md` (§113): вийшов з екрана на будь-якій фазі —
   нічого не списано, обидві фази лишаються чернеткою.

## 2. Спільний геометричний принцип: root-anchoring

Перш ніж описувати кожен тип окремо — це головний інваріант, спільний
для ВСІХ чотирьох типів, і найлегше зламати його реалізацію.

Точка, яку гравець розміщує чи тягає по зоні/кривій, — це позиція
**кореня спрайту** (точка прикріплення, визначена художником у Кроці 1
конвеєра генерації), а НЕ його геометричного центру. Але рушій
(`buildBaseComposite`) малює кожен інстанс **center-anchored**
(`item.x`/`item.y` у фінальних даних — це центр спрайту в сцені, не
корінь).

Тому клієнт **зобов'язаний** інвертувати позицію: обчислити такий зсув
центру, щоб ПІСЛЯ повороту (`item.rotation`) і масштабування
(`item.scale`) корінь спрайту опинився рівно в точці посадки, яку обрав
гравець (формула `centerAnchorForRoot` у `planting_points_editor.html`).
Якщо клієнт наївно запише `item.x/y = точка посадки` — корінь "зʼїде" з
кривої/зони при першій же зміні розміру чи повороту слайдером, і спрайт
візуально відірветься від стебла чи гілки. Це не косметична дрібниця, а
умова коректності всієх слайдерів нижче.

Кут теж рахується відносно кореня: `фінальний кут = нормаль (кривої,
зони, або вільний кут для leafFg) + rotationOffset гравця`, а
`item.rotation`, який іде у дані, — це `фінальний кут − природний кут
спрайту` (власний "куди дивиться" спрайту, обчислений одноразово в
Кроці 1 з силуету/маси пікселів, не змінюваний гравцем).

## 3. Листя — фон (`leafBg`)

**Зона:** кільце (бублик/annulus) навколо тіла кавенятка — зовнішній
контур (16-точкова замкнена крива) МІНУС внутрішній контур (теж
16-точкова замкнена крива). Точка посадки валідна, лише якщо вона
ВСЕРЕДИНІ зовнішньої межі й ОДНОЧАСНО ЗА МЕЖАМИ внутрішньої.

Чому кільце, а не суцільний круг: центр кавенятка (тіло) не повинен
заростати листям впритул — внутрішня межа тримає видиму "проплішину", де
лишається видно тіло й основи гілок.

Форма й радіуси відкалібровані по РЕАЛЬНИХ коренях 33 фонових листків
референсного дерева (`tree_layout.json`), з відступом-запасом 10px від
крайніх точок і виключенням одного статистичного викиду (лист із
z=28, що лежав явно глибше решти) — тобто зона щільно облягає реальний
розкид даних, а не намальована довільно.

| | |
|---|---|
| Кількість | **20-40** листків. Лічильник "X/20-40"; кнопка "Далі" (до фази переднього плану) неактивна, доки X<20; на X=40 зона блокує нові посадки |
| Скін | вільний вибір з каталогу 9 скінів (`leaves_batch_normal`), незалежно для кожного листка |
| Позиція | 2D drag/tap будь-де всередині кільця (не по кривій — вільна точка) |
| Поворот | **від нормалі**: базовий кут = напрямок радіус-вектора від центра кільця до точки посадки (лист "дивиться" назовні); слайдер `rotationOffset` дає зміщення **-40°...+40°**, default 0 |
| Розмір | слайдер `scale` **0.64-1.51**, default 1 |
| z-шар | спільний **z=18** для всіх bg-листків (не редагується гравцем) |

## 4. Листя — передній план (`leafFg`)

Друга фаза посадки листя (§1) — відкривається одразу після
підтвердження фону, ще без стадійного переходу й без окремого списання
препарату.

| | |
|---|---|
| Зона | звичайний суцільний полігон (без діри), невеликий, у верхній частині кільця (ближче до "лоба") — під передній акцент крони |
| Кількість | **0-5** листків. Необов'язково: 0 — просто "Пропустити" |
| Скін | той самий каталог 9 скінів |
| Позиція | 2D drag/tap у межах зони |
| Поворот | **вільний, 0-359°** — на відміну від фону, тут НЕМАЄ нормалі; лист не "дивиться" від центру автоматично, гравець крутить колесом як завгодно. Default 0° |
| Розмір | той самий `scale` **0.64-1.51**, default 1 |
| z-шар | спільний **z=53** — вище і за bg-листя (18), і за гілки (41): fg завжди малюється ПОВЕРХ, звідси й назва |

## 5. Гілки (`branch`)

**Зона:** НЕ полігон, а **відкрита крива** — дуга ~290° навколо тіла
(16 опорних точок), з вирізом ~70° знизу, де стовбур/трава (туди гілка
фізично не садиться). Корінь гілки завжди лежить РІВНО на цій кривій —
позиціювання йде через **параметр t=0..1** за довжиною дуги (повзунок
уздовж лінії, не вільний 2D drag).

`edgeBlock = 0.05`: перші й останні 5% довжини кривої заблоковані для
посадки — корінь гілки ніколи не опиняється в самому вирізі чи впритул
до його краю, де композиція виглядала б неприродно.

| | |
|---|---|
| Кількість | 2 фіксовані "руки" — рушій додає автоматично, `locked`, не показуються в цьому редакторі кривої, гравець на них не впливає; + **2-4** користувацькі гілки, які гравець садить на кривій |
| Скін | каталог 4 скіни (`branch_custom_skin1-4.png`), незалежно для кожної гілки |
| Позиція | повзунок t вздовж кривої, у межах `[edgeBlock, 1-edgeBlock]` |
| Поворот | `rotationOffset` відносно **зовнішньої нормалі кривої** в точці посадки (перпендикуляр до дотичної, напрямлений геть від тіла) — **-40°...+40°**, default 0 |
| Розмір | `scale` **1.0-1.79**, default **1.72** (гілки суттєво більші відносно свого спрайту, ніж інші типи) |
| z-шар | спільний **z=41** |

## 6. Бутони (`bud`)

Найбільша структурна зміна проти старої моделі: бутон більше не має
власної зони "навколо вже заповненого слоту" — натомість він
кріпиться до однієї з наперед заданих **кривих**:

- **крива тіла** (`budCurves.body`) — та сама геометрія/виріз/edgeBlock,
  що й крива гілок, лише в координатах сцени;
- **крива КОНКРЕТНОГО вже посадженого інстансу гілки**
  (`budCurves.bySprite[скін]`) — 1 крива для скіна 2, по 2 незалежні
  криві-"рукави" для скінів 1/3/4, у локальних координатах спрайту
  гілки (трансформуються під фактичний поворот/масштаб/позицію
  конкретного інстансу).

**Правило поєднання:** набір доступних цілей для бутона напряму
залежить від того, скільки гілок гравець посадив і які скіни обрав на
кроці 2→3. Приклад: 4 гілки скіна 1 → 1 (тіло) + 4×2 = 9 кривих-цілей;
2 гілки скіна 2 → 1 (тіло) + 2×1 = 3 цілі. Мінімум гілок — 2, тож
хоча б одна гілкова крива завжди є (крім тіла).

**Важлива відмінність від старої моделі:** бутони більше НЕ можуть
кріпитися до листків (ні фонових, ні переднього плану) — лише до тіла
або до гілки.

**UI:** усі доступні криві (тіло + кожна посаджена гілка) підсвічуються
ОДНОЧАСНО пунктиром; гравець одним drag/tap уздовж ОБРАНОЇ кривої
одночасно визначає і хазяїна (яку криву торкнувся), і позицію (t на
ній) — той самий принцип "один жест = хазяїн + позиція", що й у старій
зонній моделі (`bush_graphics_customization.md` §3), лише геометрія
тепер крива, а не зона навколо сусіднього елемента.

| | |
|---|---|
| Кількість і темп | рівно **7** сумарно, батчами по стадіях росту (без змін): №1 на переході 3→4, №2-3 на 4→5, №4-5 на 5→6, №6-7 на 6→7 |
| Скін | немає — один універсальний спрайт для стадії "бутон" (`fruit_bud_greenbean`, той самий файл, що й пізніший "зелений біб") |
| Позиція | повзунок t вздовж ОБРАНОЇ кривої, `[edgeBlock, 1-edgeBlock]` |
| Поворот | `rotationOffset` відносно нормалі обраної кривої, спільний діапазон для всіх кривих: **-60°...+60°**, default 0 |
| Розмір | `scale` **0.55-0.72**, default 0.56 (найменші з усіх елементів) |
| z-шар | **єдиний виняток**: кожен із 7 бутонів отримує СВІЙ окремий z (не спільний тип-z), послідовно за порядком посадки — №1 найдальше ззаду, №7 найближче спереду. Реальні орієнтовні значення з референс-дерева: 55, 57, 59, 60, 61, 62, 63 (конкретні числа калібрує арт-департамент під фінальний шар-стек, важливий сам принцип — зростаючий z за порядком посадки) |

**Життєвий цикл після посадки** (без дій гравця, без змін від
`bush_graphics_customization.md` §3): стадія 8 — всі 7 одночасно
`bud → flower` (випадковий скін з 5, незалежно для кожного); стадія 9 —
`flower → green_bean` (знов універсальний спрайт, без скіна); стадія 10
— `green_bean → ripe_bean` (знов випадковий скін з 5) → врожай. Усі 4
стадії плоду прив'язані до ОДНІЄЇ спільної кореневої точки (з
`fruit_bud.png`), тож позиція й кут бутона на кривій лишаються
стабільними при зміні спрайту між стадіями — гравцю ніколи не треба
підлаштовувати positioning вручну при рості плоду.

## 7. z-шари і порядок малювання — зведено

| Тип | z | Порядок серед своїх |
|---|---|---|
| leafBg | 18 (спільний) | за порядком посадки |
| branch | 41 (спільний) | за порядком посадки |
| leafFg | 53 (спільний) | за порядком посадки |
| bud | 55-63, індивідуально кожному | за порядком посадки (природно зростає) |

Порядок серед інстансів одного типу — ЧИСТО порядок посадки в масиві
(перший посаджений малюється першим, тобто найдальше ззаду). Це
детерміновано: рушій сортує `[...].sort((a,b)=>a.z-b.z)`, а стабільне
сортування (стандарт з ES2019) ніколи не переставляє елементи з
однаковим `z`. **Наслідок для UI:** порядок, у якому гравець садить
листки чи гілки в межах одного батчу, візуально важливий (пізніше
посаджений перекриває раніше посаджені) — "прибрати і посадити знову"
змінює й z-порядок, не лише позицію.

## 8. Ліміти й слайдери — зведена таблиця

| Тип | Кількість | Позиція | Поворот | Розмір | Скін |
|---|---|---|---|---|---|
| leafBg | 20-40 | 2D у кільці | offset від нормалі, -40..40° | 0.64-1.51 | 9 варіантів |
| leafFg | 0-5 | 2D у зоні | вільний, 0-359° | 0.64-1.51 | 9 варіантів |
| branch | 2-4 (+2 фікс.) | t на кривій | offset від нормалі, -40..40° | 1.0-1.79 | 4 варіанти |
| bud | 7 (батчами 1-2-2-2) | t на обраній кривій | offset від нормалі, -60..60° | 0.55-0.72 | немає |

`edgeBlock=0.05` застосовується до всіх кривих (гілкова, body-бутонна,
кожна branch-бутонна крива) — до 2D-зон (`leafBg` кільце, `leafFg`
полігон) не застосовується, бо там немає параметра t.

Жоден тип не має автоматичного захисту від накладання (мінімальної
відстані між сусідніми елементами одного типу) — посадка вільна в
межах зони/кривої, як і в старій моделі (легкий випадковий джитер при
кліку — питання остаточного UX-полірування, не геометрії).

## 9. ⚠️ Немає серверної валідації посадки

**Сервер НЕ перевіряє** координати/кут/розмір/кількість посаджених
елементів. Це свідоме рішення на зараз, і воно міняє те, що написано в
`gamification_ui.md` §113 ("Сервер перевіряє все повторно: кількість,
межі зон, скіни") — той рядок застарів, див. §12.

Практично це означає:

- **Клієнт — єдина лінія захисту.** Усі правила з §3-§8 (належність
  точки кільцю/зоні, t в межах `[edgeBlock, 1-edgeBlock]`, діапазони
  `rotationOffset`/`scale`, ліміти кількості 20-40/0-5/2-4/7,
  правильний вибір хазяїна для бутона) мають бути реалізовані на
  клієнті СУВОРО — сервер приймає й зберігає те, що прийшло, без
  повторної геометричної перевірки.
- **Наслідок:** гравець (через модифікований клієнт або прямий запит
  до API, обходячи UI) теоретично може відправити довільні координати,
  кути, розміри чи кількості, і сервер це прийме. Оскільки посаджене
  фіксується `locked: true` назавжди (`gamification_ui.md` §112), такий
  "злам" неможливо буде виправити пізніше без ручного втручання чи
  міграції даних.
- **Коли це прийнятний ризик:** немає змагального/PvP елементу, де
  неправильна посадка давала б перевагу (посадка — суто естетична
  кастомізація, не впливає на економіку `gamification_economy.md`).
  Якщо ж заплановано публічний leaderboard, шеринг кавенят чи будь-яку
  механіку, де вигляд кавенятка впливає на щось окрім самого власника —
  варто додати хоча б м'яку серверну sanity-перевірку (bounding box,
  грубі ліміти кількості) до того, як така механіка з'явиться.
- Це стосується посадки (planting/`x`,`y`,`rotation`,`scale`,
  кількостей) конкретно — не всього флоу переходів стадій: списання
  препарату й сама зміна стадії — це окремі, потенційно вже перевірені
  сервером дії (не в межах цього доку).

## 10. Розбіжності зі старою документацією

Стара геометрія листя/бутонів (`bush_graphics_customization.md` §1,
§3 і відповідні екрани в `gamification_ui.md`) описувала іншу модель,
явно позначену як орієнтовну — `bush_graphics_customization.md` прямо
відкладав ці цифри "на етап Claude Design-прототипу, не текстом" (рядки
1172-1183). Крок 3.2/4 і є цим прототипом; цей док фіксує його
результат. Розбіжності:

| | Стара модель | Нова модель (цей док) |
|---|---|---|
| Зони листя | 4 прямокутні зони (top/left/right/front), кожна з рекомендованою кількістю | 2 зони: `leafBg` (кільце навколо тіла) + `leafFg` (мала зона зверху) |
| Кількість листя | 10-16 сумарно по 4 зонах | 20-40 фон + 0-5 передній план |
| Хазяїн бутона | зона навколо будь-якого заповненого листка ЧИ гілки | лише крива тіла або крива гілки (листя виключено) |
| Спосіб посадки бутона | один tap у path, що об'єднує зони навколо хазяїв | drag/tap уздовж однієї з підсвічених кривих (тіло + кожна гілка) |
| Серверна валідація | `gamification_ui.md` §113: "сервер перевіряє все повторно" | немає (§9) |
| Гілки | 2 фіксовані + 2-4 користувацькі, 2 прямокутні зони | без змін по суті — той самий діапазон, лише зона тепер крива, не 2 bbox |

**Що варто зробити зі старими доками** (не зроблено в межах цього
запиту, лише позначено): `bush_graphics_customization.md` §1 (рядки
194-231) і §3 (рядки 264-281), а також `gamification_ui.md` рядки
115-123, 133-139 і 113 — описують геометрію, яку замінює цей док.
Конвенція репозиторію (`code/docs/README.md`: "Док, який перестав бути
правдою, не «архівується» поруч із чинними") вимагає або перенести
вміст сюди й видалити застарілі шматки, або хоча б замінити їх коротким
посиланням на цей файл — інакше в теці лишаються дві різні відповіді на
одне питання.

Природний кут спрайту в Кроці 1 не зберігається, тому його рахує скрипт:
напрямок від кореня до найдальшого непрозорого пікселя — той самий
`computeDirVector`, що й у редакторі зон. Перевірено на еталонному дереві:
36 із 37 коренів листя потрапляють у кільце (37-й — той самий викид, який
§3 виключив при калібруванні), а відхилення фінального кута від нормалі
має медіану 2,8°.

Чернетка лежить у `plants.appearance.draft` і їде на сервер із затримкою
700 мс після кожної зміни. Тому «Незавершена посадка» видно і на головному
екрані, і з іншого пристрою, а препарат при цьому не списаний. Питання
«Ти вже почав садити» показується на самому екрані посадки при вході
(у дизайні воно намальоване на HUD-екрані — зміст той самий, екраном раніше).

Добовий гейт (`plants.last_stage_transition_at`) перевіряється ще до
відкриття екрана: інакше гравець розставив би 40 листків і дізнався б про
«зарано» лише на кнопці «Посадити».

Серверні перевірки — рівно ті, що §9 називає дешевими: кількості в межах
`limits`, наявність препарату, добовий гейт, власник рослини. Геометрію
(зони, t, кути, розміри) сервер, як і домовлено, не переперевіряє.

## 11. Технічний додаток: схема `planting_placement.json`

Дані, з яких клієнт має брати зони/криві/діапазони (а не хардкодити):

```
leafBg:   { polygon[16], holePolygon[16], normalCenter{x,y}, rotationOffset{min,max,default}, scale{min,max,default}, z }
leafFg:   { polygon[4], rotationFree360:true, rotationDefault, scale{min,max,default}, z }
branch:   { path[16], normalCenter{x,y}, rotationOffset{min,max,default}, scale{min,max,default}, edgeBlock, z }
bud:      { scale{min,max,default}, rotationOffset{min,max,default}, edgeBlock }
budCurves:{ body: path[16], bySprite: { "<branch_skin>.png": [ curve[], curve[]? ] } }
```

`leafBg`/`branch`/`budCurves.body` — координати сцени (той самий
простір, що й `tree_layout.json`). `budCurves.bySprite[...]` —
координати в ЛОКАЛЬНому просторі природних пікселів спрайту гілки
(512×512), трансформуються тим самим перетворенням, що й коренева
точка гілки (`targetW=220` база, `F=targetW*scale/naturalW`, поворот на
`item.rotation` навколо центру спрайту, зсув на `item.x/y`).

Файл не версіюється в git (генерується інструментом); джерело правди —
`design/sprites/tools/planting_points_editor.html` (Крок 3.2) і сам цей
док як застигла точка на дату вище.
