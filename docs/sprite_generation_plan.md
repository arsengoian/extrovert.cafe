# План генерації спрайтів кавенятка через OpenAI Images API

Рахує, скільки окремих викликів image-generation API потрібно на ОДНУ спробу
промалювати весь перелік із `bush_graphics_customization.md` §10 (≈266-267
спрайтів), і скільки це коштуватиме. Повні цифри рядок-за-рядком — у
`Кавомат/Economics/sprite_generation_plan.xlsx` (аркуші `Generation_Plan`,
`Cost_Estimate`, `Summary`); тут — методологія й підсумок.

*12.09.2026: перша версія.*

---

## 1. Яку модель використовувати

OpenAI Images API зараз пропонує 4 GPT Image моделі: `gpt-image-2` (поточний
флагман), `gpt-image-1.5`, `gpt-image-1` і `gpt-image-1-mini`. **`gpt-image-1`
знімається з продажу 23.10.2026** — це менш ніж за два місяці від сьогодні,
тож будь-яка стаття/калькулятор, орієнтована на `gpt-image-1`, застаріє ще до
початку масової генерації. Цей план рахує на **`gpt-image-2`**.

Ключові властивості моделі для наших цілей:
- Розміри: `1024x1024` (квадрат), `1024x1536`/`1536x1024` (портрет/ландшафт),
  плюс довільні `WIDTHxHEIGHT` в межах обмежень моделі.
- Якість: `low` / `medium` / `high` (`auto` — модель обирає сама).
- **Прозорий фон** — `background: "transparent"` (preview), формат `png` або
  `webp` (не `jpeg`) — обов'язково для всіх спрайтів кущa/UI, крім Платформи
  (§10.6, суцільний фоновий елемент).
- Ціноутворення — токенне (Image input/output tokens), не пряма ціна за
  зображення; офіційна сторінка `developers.openai.com/api/docs/pricing`
  відсилає до калькулятора в гайді, а не дає готову таблицю $/зображення для
  кожного розміру. Конкретні $/зображення нижче — з незалежних агрегаторів
  (OpenRouter, aifreeapi, buildmvpfast, costgoat), що перерахували токенну
  ціну в $/зображення й узгоджуються між собою; звірити перед масовим
  запуском, якщо ціна принципова для бюджету.

## 2. Конвенція розмірів у пікселях

У доку графіки (§0) кожна кастомізована частина (листок/гілка/плід) вже
описана як **окремий маленький спрайт з нормалізованими x/y-координатами**,
розміщений і повернутий рушієм у момент рендеру — не суцільний шар на весь
канвас. Це означає, що розмір ФАЙЛУ спрайта не мусить дорівнювати розміру
персонажа — досить розміру, якого вистачить для чіткого відображення тієї
частини екрана, яку займає ця деталь.

Умовний **майстер-канвас персонажа = 1024×1024** (те саме "canvas-бокс
шаблону стадії" з §0). Звідси — 4 практичні бакети фінального розміру
спрайта (усі — квадратні PNG з альфа-каналом, крім Платформи):

| Бакет | px | Що сюди потрапляє |
|---|---|---|
| XL | 1536×1024 | Платформа (§10.6) — єдиний широкий фоновий елемент |
| L | 512×512 | Стовбур/ранні стадії (§10.1), гілки (§10.4), бочка+поличка (§10.6), крейт-деталі (§10.9), VFX-атлас (§10.14) |
| M | 256×256 | Листя (§10.3), плоди (§10.5), відро+крапля (§10.7), одяг (§10.13) |
| S | 128×128 | Обличчя (§10.2), хмаринка+іконки-хочу+AI-чат (§10.8), валюта (§10.10), іконки магазину (§10.11), UI гардеробу (§10.12) |

Усі генерації нижче виконуються на канвасі **1024×1024** (або 1536×1024 для
Платформи) незалежно від фінального бакета — після нарізки кожна комірка
просто масштабується ВНИЗ до потрібного фінального розміру. Це свідомо
консервативний вибір: завжди є запас роздільності, ніколи не треба
апскейлити розмитий кадр.

## 3. Як групуються спрайти в одну генерацію

Один виклик API повертає ОДНЕ зображення. Щоб не витрачати 266 окремих
викликів на 266 спрайтів, спорідненні спрайти генеруються РАЗОМ як
"референс-аркуш" (grid із кількох підписаних комірок), а потім нарізаються
скриптом (Python/Pillow) на окремі PNG — той самий підхід, що вже дав добрий
результат на раніше згенерованих референсах (`design/sprites/reference/`,
напр. `row.jpeg` — аркуш із кількома варіантами в одному зображенні).

Правило групування — баланс двох ризиків:
- **Занадто велика група** → модель "змішує" стилі різних елементів в одній
  комірці, або дрібні деталі (наприклад зіниці ока) втрачають чіткість.
- **Занадто дрібна група** → більше окремих викликів, вища сумарна ціна,
  більше шансів на стилістичну розбіжність МІЖ генераціями (той самий
  листковий скін у різних викликах може вийти трохи іншим за тоном).

Звідси — три патерни групування, застосовані по всьому переліку §10:

1. **"Один об'єкт, кілька станів"** — усі пози/mood-варіанти ОДНІЄЇ сутності
   в одному аркуші, де стилістична єдність найважливіша. Приклад: 7 деталей
   обличчя одного набору для одного mood-стану (§10.2, 15 генерацій = 5
   наборів × 3 стани); 3 пози одного листкового скіна (§10.3, 10 генерацій).
2. **"Реєстр варіантів"** — серія РІЗНИХ дизайнів одного типу об'єкта, де
   аркуш явно проситься як "5 варіантів X" (те, що вже подобається в
   референсах ChatGPT). Приклад: 5 скінів квітки, 5 скінів стиглого бобу,
   15 комплектів одягу (по 5 предметів кожен, §10.13 — 15 генерацій = 75
   предметів, ідеально лягає на вже задокументовану структуру "15 наборів").
3. **"Плоский іконковий сет"** — дрібні, прості, малодеталізовані UI-іконки
   без ризику стильового розмиву (валюта, іконки магазину, іконки хмаринки)
   — можна класти по 6-8 у ОДНУ генерацію.

## 4. Підсумок: 56 генерацій на 267 спрайтів

| | Значення |
|---|---|
| Спрайтів усього (§10) | 267 (доку діапазон ≈266-267 — розбіжність ±1 через "5-6" у §10.12, тут узято 6) |
| Генерацій (1 спроба, без перегенерацій) | **56** |
| Вартість — усе на `low` | **$0.34** |
| Вартість — усе на `medium` | **$3.00** |
| Вартість — усе на `high` | **$11.92** |
| Вартість — рекомендований мікс | **≈$7.45** |

**Рекомендований мікс** — `high` для двох категорій, де якість найбільше
впливає на сприйняття гравцем і продаваність (Обличчя §10.2 — 15 генерацій,
Одяг §10.13 — 15 генерацій), `medium` для решти "тіла" куща й реквізиту
(стовбур, гілки, листя, плоди, крейт, VFX), `low` для плоских UI-іконок
(валюта, магазин, хмаринка, гардероб UI, полив, бутон/зелений біб).

Навіть максимальний варіант (усе на `high`, $11.92) — тривіальна сума в
абсолютних грошах. Головний бюджетний ризик тут не в ціні генерації, а в
**кількості спроб**: наведені $0.34-$11.92 рахують РІВНО 1 виклик на групу.
Реалістичний перший прохід по всьому переліку — з переробкою частини
аркушів через невдалий стиль/композицію — варто закладати з буфером
**×1.5-2** (тобто орієнтовно $11-24 для рекомендованого міксу, і досі
копійки в масштабі проєкту).

## 5. Що лишається поза вартістю API

- **Нарізка аркуша на окремі спрайти** — Python/Pillow скрипт по заданих
  координатах комірок (координати комірок відомі наперед, бо grid і
  підписи задаються в промпті) — безкоштовно, локально.
- **Перевірка прозорості фону** — `background: "transparent"` у preview,
  тож варто прогнати автоматичну перевірку (альфа-канал не 100% по краях)
  і за потреби докрутити вручну/скриптом (напр. `rembg` як страхувальний
  запасний варіант, якщо нативна прозорість підведе на конкретному аркуші).
- **Перегенерації за якістю** — див. буфер ×1.5-2 вище.
- **Фінальний "granular QA"-прохід** художника/дизайнера по всьому сету
  перед інтеграцією в гру — ручна праця, не рахується тут.
