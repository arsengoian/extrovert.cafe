# Викочування

*Написано 21.09.2026, коли зʼявився перший застосунок, який є куди викочувати.*

Три різні речі їдуть трьома різними шляхами, і плутати їх не варто:

| Що | Куди | Чим |
|---|---|---|
| застосунок гравця (`client`) | Cloudflare Workers, статика + SPA-фолбек | `bun run deploy:client` |
| переадресація з QR-наклейки (`qr`) | Cloudflare Workers, лише 302 | `make deploy-qr` (§1) |
| DNS, бакети R2, домени воркерів | Cloudflare | terraform, той самий стан, що й дроплет (§2.1–2.2) |
| бекенд (`api`, `ws`, `checkbox`, `scheduler`, `overseer`) | дроплет, docker compose | розділ 2 |
| меню точок | публічний бакет R2 | котить `scheduler` за деплойментом з адмінки (`services.md` §4) |
| релізи кіоска | публічний бакет R2 | GitHub Actions, робота `kiosk-release` (§2.3) |

## 1. Застосунок гравця → Cloudflare Workers

```bash
bun run deploy:client:dry     # зібрати й перевірити, нічого не викочуючи
bun run deploy:client         # зібрати, перевірити, викотити
```

Скрипт (`scripts/deploy-client.mjs`) робить те, чого не робить сам
`wrangler`:

1. читає `frontend/client/.env.production` і вимагає `VITE_API` на `https`, а `VITE_WS` — на `wss`;
2. збирає Vite;
3. **шукає в зібраному бандлі `localhost:3001`** і зупиняється, якщо
   знайшов. Адреса api зашивається в бандл на етапі збірки: один викочений
   прод із локальною адресою — і живий сайт стукає в ноутбук розробника,
   а дізнаємось ми про це зі скарг;
4. каже, чи є маршрут у `wrangler.toml` — тобто чи перехопить цей деплой
   продовий домен.

**Домени воркерів привʼязує terraform** (22.09.2026,
`cloudflare_workers_custom_domain` в `infra/terraform/cloudflare.tf`):
`extrovert.cafe`, `admin.`, `qr.`, `r.`. wrangler лише заливає код, тож
прив'язка прод-домену — рішення, яке видно в `make tf-plan`, а не побічний
ефект випадкового деплою. У `wrangler.toml` `routes` навмисно закоментовані.
Рядок стоїть до першої таблиці (`[assets]`, `[vars]`): після заголовка
таблиці TOML поклав би його в неї (`assets.routes`), і маршрут мовчки не
застосувався б. `deploy-client` розбирає `wrangler.toml` і зупиняється,
якщо бачить таке.

Цілі `make deploy-admin`, `deploy-qr`, `deploy-redirect` запускають bun із
`--env-file=.env`: з `--filter` скрипт стартує в теці пакета, де `.env`
немає, і wrangler без `CLOUDFLARE_API_TOKEN` просить логін у браузері.

Що ще лишається:

- `extrovert.cafe/r/*` — поки що це SPA-фолбек самого застосунку (сторінка
  стукає в api й веде гостя далі). Якщо захочемо справжній 302 без JS —
  окремий Worker на цей маршрут;

### Адмінка → ті самі Workers

```bash
make deploy-admin-dry
make deploy-admin
```

Адмінка (`frontend/admin/`) — така сама статика, як застосунок гравця: свого сервіса
в бекенді вона не має й не потребує, бо все, що робить, — показує дані з
api (`/admin/overview`). Домен — `admin.extrovert.cafe`, його привʼязує
terraform; у `api` цей origin уже дозволений CORS-ом. `deploy` адмінки
спершу збирає Vite — раніше він заливав той `dist`, що лежав.

Справжнього входу ще немає: поки що працює девелоперський (`POST
/admin/dev-login`, вимкнений поза local), а в проді сторінка чесно каже, що
входу нема. Це навмисно: заглушка без входу безпечніша за заглушку з
напівзробленим входом.

### QR-наклейка → воркер `qr`

```bash
make deploy-qr-dry   # зібрати й перевірити, нічого не викочуючи
make deploy-qr       # викотити на qr.extrovert.cafe
```

`frontend/qr` — воркер без статики: будь-який запит на `qr.extrovert.cafe`
отримує 302 на `extrovert.cafe/` із тим самим query (`?p=1` з наклейки).
Домен, як і в решти воркерів, привʼязує terraform: Workers самі заводять
під нього DNS-запис і сертифікат, руками в дашборді робити нічого. Чому
воркер, а не правило переадресації, — `urls.md`.

## 2. Бекенд → дроплет

Два дроплети в FRA1, у спільному VPC (обґрунтування — `video.md`
«Чому два дроплети»):

| | `public` | `analysis` |
|---|---|---|
| Розмір | **2 vCPU / 4 ГБ**, ~$24/міс | **1 vCPU / 2 ГБ**, ~$12/міс |
| Що крутить | `api`, `ws`, `checkbox`, `scheduler`, `overseer`, `glitchtip`, `postgres`, `redis` | `worker` відео — і більше нічого |
| Публічні порти | 80/443 | **жодного** |
| Коли потрібен | одразу | лише коли дійде до відео з камер |

Тобто на старті вистачає **одного** дроплета за $24. Postgres і Redis
живуть у докері поруч — свідома економія; умови переїзду на керовану базу
описані у `video.md`.

Дві речі, які роблять до першого деплою:

1. **файрвол DigitalOcean**, не `ufw`: докер пише власні правила в iptables
   повз нього, і `ufw` створює ілюзію захисту;
2. **прибити Postgres і Redis до петлі** — у `docker-compose.yml` вони
   опубліковані на всі інтерфейси (`5442:5432`, `6389:6379`), що на
   публічному дроплеті означає базу в інтернеті.

Доступ — ключем із `keys/` (`make keys-ssh` покаже публічну частину):
пароль для входу на сервері має бути вимкнений.


**Коду на сервері немає.** Сервіси зібрані одним `docker/bun.Dockerfile`
(аргумент `SVC`), але збирає їх GitHub Actions, а на дроплет приїжджають
готові образи. На самому сервері лежить рівно три речі: `docker-compose.yml`
(симлінк на `docker-compose.prod.yml`), `.env` і томи докера. Як це
працює — §2.3.

Що лишилось ручним і чому: **міграції окремим кроком**, до підняття нової
версії сервісів (`docker compose run --rm migrate up` — це робить
`rollout.sh`). У compose вони описані як залежність, але запускати їх разом
із рестартом означає чекати на них у кожного сервіса окремо й не бачити
помилку в окремому виводі.

### Що має бути в `.env` на сервері

**`.env.prod`** (22.09.2026) — оточення сервера. Живе на машині розробника
поруч із `.env` (у git його немає) і їде на сервер цілим файлом:

```bash
make env-prod-check   # ключі й порядок — як у .env.example
make env-push         # /opt/extrovert/.env.prod, а .env — симлінк на нього
```

Зібраний раз зі звичайного `.env` (`bun scripts/env-prod.mjs init`) і далі
правиться руками. Від локального відрізняється тим, що:

- адреси й оточення продові (`APP_ENV=production`, `APP_ORIGIN`,
  `REDIS_URL=redis://redis:6379` — його читає й GlitchTip);
- секрети, які ми генеруємо самі, свої: `POSTGRES_PASSWORD`,
  `JWT_PRIVATE_KEY` (локальний ключ, що підписує й прод, дозволяв би з
  ноутбука випускати токени для живих гравців), `GLITCHTIP_SECRET_KEY`;
- `OPENAI_VECTOR_STORE` — окреме прод-сховище `extrovert-kb-production`;
- порожнє все, що потрібне лише розробнику: тестові облікові записи Checkbox
  (`*_TEST_*`), MinIO (`R2_DEV_*`), `CLOUDFLARE_*`, `DIGITALOCEAN_API_KEY`,
  `GHCR_TOKEN`, `DATABASE_URL_LOCAL`. На сервері цих ключів бути не повинно.

`MONO_TOKEN` і `OPENAI_API_KEY` поки ті самі, що локально (тестові) —
бойові власник поставить сам.

`TAG` на сервері пише `rollout.sh` (`sed -i --follow-symlinks`, щоб не
замінити симлінк файлом), а `env-push` цей рядок зберігає — локальний файл
про версію, що крутиться, не знає.

Ключі, без яких частина сервісів мовчки нічого не робить:

| Ключ | Без нього |
|---|---|
| `JWT_PRIVATE_KEY` | api не стартує: тимчасовий ключ у проді розлогінював би всіх на кожному рестарті |
| `MAILGUN_API_KEY`/`DOMAIN`/`API` | вхід поштою відповідає 503 — гравці не можуть увійти. `MAILGUN_API` — за регіоном домену (`api.eu.mailgun.net` для EU) |
| `OPENAI_API_KEY` | чат кавенятка відповідає уривками бази знань |
| `NP_API_KEY` | scheduler не оновлює довідник і не трекає посилки |
| `CHECKBOX_LOGIN`/`PASSWORD` | checkbox не опитує чеки |
| `CHECKBOX_LICENSE_KEY` | вебхук Checkbox не зареєструвати (сам ключ підпису лежить у базі, §3) |
| `TELEGRAM_BOT_TOKEN`/`CHAT_ID` | overseer пише алерти лише в лог |
| `SUPPORT_BOT_USERNAME` | кнопка «Підтримка» каже, що підтримка ще не підключена |
| `SUPPORT_BOT_TOKEN`/`SECRET` | бот підтримки мовчить: вебхук не реєструється, відповісти з адмінки нема чим |

`.env.example` тримає тестові ключі Checkbox поруч зі справжніми навмисно —
щоб зменшити шанс випадково смикнути бойовий ПРРО.

## 2.1 Дроплет і файрвол через terraform

Сервер піднімає `infra/terraform`, не рука в панелі DigitalOcean: інакше
через місяць ніхто не скаже, звідки взялося правило файрвола. Токен
береться з `.env` (`DIGITALOCEAN_API_KEY`) обгорткою `scripts/tf.mjs` — у
лог і в аргументи процесу він не потрапляє.

```bash
make tf-plan      # що зміниться
make tf-apply     # дроплет, файрвол, привʼязка до проекту extrovert.cafe
make tf-output    # адреси й готова команда входу
make ssh-public   # зайти на сервер
```

Що описано: дроплет `extrovert-public` (1 vCPU / 2 ГБ, FRA1, Ubuntu 24.04)
зі swap-файлом на 2 ГБ і докером, файрвол `extrovert-public-fw` (вхідні
22, 2222, 80, 443, icmp) і привʼязка до проекту `extrovert.cafe`. Ключі
доступу — наш `keys/extrovert_ed25519` плюс ключі людей із акаунта
DigitalOcean за іменем (`ssh_key_names`). DO кладе ключі **лише при
створенні** дроплета: додати людину пізніше = дописати ключ у
`authorized_keys` руками.

**Чому ssh слухає ще й 2222.** З частини мереж вихідний 22 закритий —
21.09.2026 з робочої машини не відкривався навіть `github.com:22`. В
Ubuntu 24.04 ssh за замовчуванням запускає systemd через socket-активацію,
і директиву `Port` вона ігнорує; спроба додати порт у сам юніт сокета
перевірена на окремому дроплеті й закінчилась тим, що юніт лишився
`active`, не слухаючи **нічого** — навіть 22. Тому cloud-init вимикає
`ssh.socket` і вмикає класичний `ssh.service`, який `Port` розуміє.

**Головна пастка: user-data має бути тільки з ASCII.** DigitalOcean передає
cloud-init через config drive, і один не-ASCII символ — навіть у коментарі —
ламає його так, що cloud-init **мовчки не виконує нічого**: ні ssh на
запасному порту, ні докера, ні жодного повідомлення про помилку. Дроплет
при цьому здоровий і відповідає на 22. Доведено 21.09.2026 парою зондів:
мінімальний конфіг із єдиним рядком «# коментар кирилицею» не виконався,
той самий повний конфіг без не-ASCII — виконався цілком. Тому коментарі в
`cloud-init.yaml.tftpl` англійською, а пояснення «чому» — тут. Щоб це не
повторилось, у `main.tf` стоїть `precondition`, який валить `plan` з
поясненням, щойно в user-data зʼявиться не-ASCII.

**Пакети ставляться з `runcmd`, а не модулем `packages`.** Модуль пакетів
виконується до `runcmd`, а apt на першому завантаженні бореться за
dpkg-лок із власним `unattended-upgrade` образу — і весь цей час немає ні
ssh на запасному порту, ні докера. Тепер перший крок `runcmd` — ssh, і
лише потім apt (із `DPkg::Lock::Timeout`, щоб не падати на зайнятому локу).

Якщо сервер після створення мовчить — `terraform apply -var
debug_beacon=true`: перші 15 хвилин дроплет віддає на :80 стан cloud-init,
список портів і хвіст `cloud-init-output.log`, після чого вимикає це сам.

Стан terraform лежить локально й у git не їде (`infra/terraform/.gitignore`
пояснює чому). Наслідок памʼятати треба: `apply` із чистої копії репозиторію
підніме **другий** дроплет замість того, щоб побачити наявний. На новій
машині спершу `terraform import digitalocean_droplet.public <id>`.

**Cloudflare — у тому самому стані** (22.09.2026, `cloudflare.tf`):
записи `api`/`ws`/`errors` → дроплет (адреса береться з ресурсу дроплета,
тож новий сервер = новий план DNS), записи Mailgun, бакети R2 із CORS,
lifecycle і блокуванням, домени воркерів. Токен рівня акаунта з `.env`
(`CLOUDFLARE_API_TOKEN`, `CLOUDFLARE_ACCOUNT_ID`). В акаунті багато
стороннього, і terraform бачить лише описане: зону він не керує (лише
записи в ній), чужих бакетів і воркерів не знає. Те, що існувало раніше
(записи Mailgun, бакет `extrovert-pos`), імпортоване блоками `import` —
план після імпорту не показав жодної різниці. На бакетах і записах пошти
стоїть `prevent_destroy`.

Поза terraform навмисно: `pos.extrovert.cafe` — старий воркер
`extrovert-pos`, з якого кіоск на kyiv-01 досі бере меню (`services.md`
§5). Прибрати його можна лише разом зі зміною `config/env` на малині.

Чого terraform **не** робить: вміст `.env` на сервері (`make env-push`,
вище) і код воркерів (wrangler, §1).

## 2.2 Бакети R2

**П'ять** бакетів, по одному на призначення, усі описані в terraform
(`infra/terraform/cloudflare.tf`, 22.09.2026). Дев-копій у хмарі немає:
локально їх замінює MinIO з compose (`services.md` §2.1).

**Юрисдикція — default, розташування EEUR**, а не EU jurisdiction, як
планувалось: `extrovert-pos` уже жив у default, а EU-бакети мають інший
S3-ендпоїнт (`<акаунт>.eu.r2.cloudflarestorage.com`). Бакети в різних
юрисдикціях вимагали б двох ендпоїнтів і двох наборів ключів у
`lib/r2.js`. EEUR — підказка розташування (Східна Європа), не юридична
гарантія; якщо колись знадобиться саме EU jurisdiction — переїзд усіх
бакетів разом, зі зміною `R2_ENDPOINT`.

| Бакет | Налаштування (terraform) |
|---|---|
| `extrovert-pos` | меню й релізи. Публічного доступу й домену `pos.extrovert.cafe` на самому бакеті поки немає: домен тримає старий воркер (§2.1) |
| `extrovert-uploads` | **CORS**: `PUT` з `https://extrovert.cafe`, заголовок `content-type`. Lifecycle не заводимо: фото зі скарг живуть без обмеження (рішення власника 21.09.2026) |
| `extrovert-backups` | щоденні дампи Postgres (§2.4), lifecycle 30 днів |
| `extrovert-video` | lifecycle 7 днів + bucket lock на 7 днів |
| `extrovert-evidence` | без обмеження |
| усі | ключ доступу лише для сервера; на машині розробника прод-ключів тримати не треба |

CORS для `extrovert-uploads` обовʼязковий: телефон заливає фото **напряму**
в бакет за підписаним посиланням, і без CORS браузер навіть не спробує.

## 2.3 Викочування: образи, реєстр, перемикання без розриву

### Що лежить на сервері

```
/opt/extrovert/
  docker-compose.yml        → симлінк на docker-compose.prod.yml
  docker-compose.prod.yml   ← кладе CI з репозиторію
  .env                      ← руками, один раз
```

І все. Ні коду, ні `git pull`, ні збірки на дроплеті з 1 vCPU. Відповідно
сервіси не мають права писати щось на диск поза томами й читати файли, яких
немає в образі: логи йдуть у stdout (`backend/lib/src/log.js`), дані читаються з
`backend/api/data/`, що поїхало в образ разом із кодом.

Два compose-файли, а не один із профілями: локально сервіс — це `build:` з
відкритими портами й монтуванням теки, у проді — незмінний образ із тегом,
без жодного bind-mount і майже без публічних портів. Різниця не в наборі
сервісів, а в природі опису.

### Реєстр

Образи — у `ghcr.io/arsengoian/extrovert-<сервіс>`: api, ws, checkbox,
scheduler, overseer, migrate, caddy. Фронтенди (клієнт, адмінка, редирект)
у цей список не входять — вони на Workers. Тег — **sha комміта**; `latest`
теж ставиться, але деплой завжди їде на точний sha, інакше на питання «що
зараз крутиться» немає відповіді, а відкат неможливий.

Скільки це коштує: публічні пакети в ghcr безкоштовні без обмежень, приватні
на безкоштовному тарифі мають **500 МБ сховища** (спільно з артефактами
Actions) і **1 ГБ вихідного трафіку на місяць**; завантаження з самого
GitHub Actions у трафік не рахується, а от `docker pull` на дроплет —
рахується. Наші образи: api/checkbox 139 МБ, ws/overseer 132,
migrate 96, scheduler 89, caddy 63 — це в розпакованому вигляді, реєстр
зберігає стиснені шари й однакові шари не дублює. Один набір версій
вкладається в 500 МБ, а кожен наступний коміт додає лише шар з кодом
(сотні кілобайт), бо шар залежностей той самий. Щоб це лишалось правдою,
у workflow є крок `cleanup`: більше пʼяти версій на пакет не тримаємо.
Якщо колись перестане вкладатись — варіанти в порядку розумності: платити
($0.25 за ГБ сховища), винести реєстр на дроплет, або зробити пакети
публічними (останнє — тільки якщо код перестане бути приватним).

### Як їде нова версія

Пуш у `main` запускає `.github/workflows/deploy.yml`:

1. **build** — матриця з семи образів, кеш шарів у GitHub Actions;
2. **deploy** — копіює `docker-compose.prod.yml`, ставить симлінк, логінить
   сервер у ghcr і віддає `docker/rollout.sh` **через stdin**: скрипт на
   сервері не лишається, щоб не розійтися з репозиторієм;
3. **cleanup** — прибирає старі версії пакетів.

`rollout.sh` робить перемикання без розриву — це головне, заради чого
з'явився caddy:

- записує `TAG=<sha>` у `.env`, щоб будь-який ручний `docker compose` на
  сервері бачив ту саму версію;
- тягне образи, піднімає базу, прокочує міграції;
- для `api`, `ws`, `checkbox` піднімає **другий контейнер поруч зі старим**
  (`--scale <svc>=2 --no-recreate`), чекає на його healthcheck і лише тоді
  гасить старий через `docker stop -t 30`;
- решту сервісів просто перезапускає: у них або немає зовнішнього трафіку,
  або є порт хоста, тобто двох копій одночасно бути не може.

Чому це працює миттєво: сервіси за проксі не публікують портів, тому дві
копії живуть поруч. Caddy ходить у них не за фіксованою адресою, а через
`dynamic a` — перепитує вбудований DNS докера кожні дві секунди, тож новий
контейнер потрапляє в пул одразу. Старий у цей час отримує SIGTERM: нових
зʼєднань не бере, а взяте доробляє до 30 секунд (`backend/lib/src/shutdown.js`,
`stop_grace_period` у compose). Для клієнта перемикання виглядає як
звичайний запит — у найгіршому випадку одна спроба зʼєднання відвалюється,
і caddy повторює її на сусідній копії (`lb_try_duration`).

Якщо новий контейнер не став healthy — скрипт прибирає його й лишає стару
версію працювати. Деплой падає, прод живий.

### Реліз кіоска

Окрема робота `kiosk-release` у тому самому workflow. Вона збирає ARM-бінарник
під armv6 (той самий Raspbian Stretch, що на пристрої, через QEMU), пакує
архів і кладе його в публічний бакет під `releases/pi/` — архів першим,
маніфест останнім, інакше точка піде по архів, якого ще немає
(`raspberry-pi.md` §3).

**Збирається лише тоді, коли змінився код.** Робота рахує хеш
`raspberry/kiosk` + `raspberry/pi/stack` і звіряє з полем `source` у вже
опублікованому маніфесті: збіглось — пропускаємо все, включно з QEMU-збіркою
(вона повільна). Джерело правди тут — сам бакет, а не пам'ять CI: точка бере
реліз звідти, і звіряти треба з тим, що бачить вона.

Так само пропускаються й образи сервісів: кожен рахує хеш своїх тек
(`backend/<сервіс>`, `backend/lib`, Dockerfile, `package.json`, `bun.lock`)
і шукає в реєстрі тег `src-<хеш>`. Знайшовся — замість збірки на нього
вішаються теги цього комміта (`docker buildx imagetools create` робить це на
боці реєстру, шари нікуди не їдуть). Комміт у один сервіс більше не
перезбирає всі сім і не з'їдає квоту реєстру.

### Секрети, які треба завести в GitHub

| Секрет | Навіщо |
|---|---|
| `SSH_PRIVATE_KEY` | вміст `keys/extrovert_ed25519` — ним CI заходить на дроплет |
| `SERVER_HOST` | адреса дроплета (`make tf-output`) |
| `SERVER_PORT` | `2222`, якщо не задано |
| `SERVER_USER` | `root`, якщо не задано |
| `GHCR_TOKEN` | токен із `write:packages`: ним CI пушить образи (без нього — `GITHUB_TOKEN`) і логінить сервер у ghcr, щоб той тягнув приватні образи. Без секрету деплой вважає, що сервер уже залогінений. act бере його з локального `.env` (через `.secrets`) і для пушу, і для логіну сервера |
| `R2_ENDPOINT`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY` | заливка релізу кіоска в публічний бакет. Лише ці три — і лише в CI: на точку ключі не потрапляють ніколи |
| `OPENAI_API_KEY`, `OPENAI_VECTOR_STORE` | робота `knowledge`: після `kb:check` синхронізує базу знань чату з vector store (`kb:push`, лише змінене). Без них робота тільки перевіряє базу, під act — теж |

### Той самий деплой локально

```bash
make act-secrets   # .secrets із локального .env, ключа й стану terraform
make act-build     # збирає всі образи, нічого не пушить
make act-deploy    # справжнє викочування на живий сервер
```

`.secrets` у git не потрапляє — у ньому приватний ключ від сервера. Під act
шлях той самий, що й у CI (рішення власника 22.09.2026): збірка логіниться
в ghcr токеном `GHCR_TOKEN` із `.secrets` і пушить образи з тегом поточного
коміту, `act-deploy` їх викочує. Раніше act образів не пушив — і локальний
прогін не міг викотити нічого. Відрізняються лише кеш збірки (GitHub
Actions cache локально недоступний), реліз кіоска й прибирання реєстру: під
act вони не виконуються.

Виняток — робота `knowledge` (`make act-knowledge`): під act вона так само
синхронізує прод-сховище OpenAI, ключами з `.secrets` (`act-secrets` бере
`OPENAI_API_KEY` і `OPENAI_VECTOR_STORE` з `.env.prod`). `oven-sh/setup-bun@v2`
тепер на Node 24, і act 0.2.59 його не запускає — потрібен act ≥ 0.2.8x.

### DNS, який має існувати

Усі — в terraform (§2.1). `api`, `ws`, `errors` — A і AAAA на дроплет, без
проксі Cloudflare; сертифікати Caddy бере сам. `mail.extrovert.cafe` —
записи Mailgun (SPF, DKIM, DMARC, MX, CNAME трекінгу), заведені руками й
імпортовані: без SPF і DKIM листи для входу частіше падають у «Спам», а це
і є єдиний вхід. Записи під домени воркерів заводить сам Cloudflare.

Проксіювати `api` через Cloudflare варто заради Safari: інакше сесія на
iPhone може жити 7 днів замість 180 (`services.md` §3).

## 2.4 Бекапи бази

Раз на добу `scheduler` робить `pg_dump` у форматі custom і кладе в
`extrovert-backups` як `postgres/<дата UTC>.dump`
(`backend/scheduler/src/jobs/backup.js`). Робота щогодини питає бакет, чи є
вже сьогоднішній файл: пропущена ніч наздоганяється тієї ж години, як
scheduler піднявся, і двічі за добу дамп не робиться. Lifecycle бакета
тримає 30 днів. `pg_dump` — в образі scheduler (`postgresql16-client` у
`docker/bun.Dockerfile`), тієї ж мажорної версії, що й сервер: піднімуть
postgres у compose — піднімати й тут.

Відновлення — на сервері, з дампа, скачаного з R2:

```bash
docker compose exec -T postgres pg_restore -U extrovert -d extrovert --clean --if-exists --no-owner < 2026-09-22.dump
# одна таблиця замість усієї бази:
docker compose exec -T postgres pg_restore -U extrovert -d extrovert --clean --if-exists --no-owner -t users < 2026-09-22.dump
```

Перевірено 22.09.2026 на локальній базі: дамп у MinIO, `pg_restore --list`
бачить дані всіх 46 таблиць.

## 3. Після першого викочування

- зареєструвати вебхук Checkbox:
  `docker compose exec checkbox bun run webhook:register --set --prod` —
  потрібен `CHECKBOX_LICENSE_KEY`; ключ підпису скрипт кладе в базу
  (`webhook_keys`), у `.env` його писати не треба. Після цього `overseer`
  почне бачити `last_error_date` і скаржитись, коли вебхуки до нас не доходять;
- база GlitchTip: `rollout.sh` створює її сам (`createdb glitchtip`, якщо
  немає) — postgres на першому старті заводить лише свою. Реєстрація в
  GlitchTip відкрита для першого користувача: зареєструватись треба
  відразу, як `errors.extrovert.cafe` відповів;
- вебхук бота підтримки `api` реєструє сам на старті, щойно в `.env` є
  `SUPPORT_BOT_*`; перевірити — `docker compose exec api bun run support:webhook`
  (адреса, черга, остання помилка);
- база знань чату в OpenAI: прод-сховище `extrovert-kb-production`
  створене 22.09.2026 (`make kb-store APP_ENV=production OPENAI_VECTOR_STORE=`
  — порожнє значення, щоб не заважав локальний id із `.env`) і заповнене.
  Його id лежить у `.env.prod`, а для CI — у секреті GitHub
  `OPENAI_VECTOR_STORE` поруч з `OPENAI_API_KEY`; далі сховище наздоганяє
  репозиторій саме, на кожен пуш у `main` (робота `knowledge`);
- перевірити, що `scheduler` справді публікує `outbox`: рядки з
  `published_at is null` не мають накопичуватись.
