# Викочування

*Написано 21.09.2026, коли зʼявився перший застосунок, який є куди викочувати.*

Три різні речі їдуть трьома різними шляхами, і плутати їх не варто:

| Що | Куди | Чим |
|---|---|---|
| застосунок гравця (`client`) | Cloudflare Workers, статика + SPA-фолбек | `bun run deploy:client` |
| бекенд (`api`, `ws`, `checkbox`, `scheduler`, `overseer`) | дроплет, docker compose | розділ 2 |
| меню й релізи кіоска | публічний бакет R2 | `bun run --filter @extrovert/pos prices:push` / `release:push` (`pos/README.md`) |

---

## 1. Застосунок гравця → Cloudflare Workers

```bash
bun run deploy:client:dry     # зібрати й перевірити, нічого не викочуючи
bun run deploy:client         # зібрати, перевірити, викотити
```

Скрипт (`scripts/deploy-client.mjs`) робить те, чого не робить сам
`wrangler`:

1. читає `client/.env.production` і вимагає `VITE_API` на `https`;
2. збирає Vite;
3. **шукає в зібраному бандлі `localhost:3001`** і зупиняється, якщо
   знайшов. Адреса api зашивається в бандл на етапі збірки: один викочений
   прод із локальною адресою — і живий сайт стукає в ноутбук розробника,
   а дізнаємось ми про це зі скарг;
4. каже, чи є маршрут у `wrangler.toml` — тобто чи перехопить цей деплой
   продовий домен.

**Домен привʼязується один раз у дашборді Cloudflare.** У `wrangler.toml`
`routes` навмисно закоментовані: поки їх немає, деплой їде на
`*.workers.dev`, і випадковий запуск скрипта не забирає `extrovert.cafe`.

Що ще потрібно зробити руками один раз:

- `api.extrovert.cafe` → дроплет (A/AAAA), інакше застосунок зʼїде на CORS;
- `extrovert.cafe/r/*` — поки що це SPA-фолбек самого застосунку (сторінка
  стукає в api й веде гостя далі). Якщо захочемо справжній 302 без JS —
  окремий Worker на цей маршрут;
- `qr.extrovert.cafe` — запис `AAAA 100::` і правило переадресації
  (`urls.md`); наклейка вже надрукована, а хоста ще немає.

## 2. Бекенд → дроплет

Два дроплети в FRA1, у спільному VPC (обґрунтування — `video.md`
«Чому два дроплети»):

| | `public` | `analysis` |
|---|---|---|
| Розмір | **2 vCPU / 4 ГБ**, ~$24/міс | **1 vCPU / 2 ГБ**, ~$12/міс |
| Що крутить | `api`, `ws`, `checkbox`, `scheduler`, `overseer`, `glitchtip`, `postgres`, `redis` | `worker` відео — і більше нічого |
| Публічні порти | 80/443 | **жодного** |
| Коли потрібен | одразу | лише коли дійде до відео з камер |

Тобто на старті вистачає **одного** дроплета за $24. Postgres і Redis
живуть у докері поруч — свідома економія; умови переїзду на керовану базу
описані у `video.md`.

Дві речі, які роблять до першого деплою:

1. **файрвол DigitalOcean**, не `ufw`: докер пише власні правила в iptables
   повз нього, і `ufw` створює ілюзію захисту;
2. **прибити Postgres і Redis до петлі** — у `docker-compose.yml` вони
   опубліковані на всі інтерфейси (`5442:5432`, `6389:6379`), що на
   публічному дроплеті означає базу в інтернеті.

Доступ — ключем із `keys/` (`make keys-ssh` покаже публічну частину):
пароль для входу на сервері має бути вимкнений.


Сервіси зібрані одним `docker/bun.Dockerfile` (аргумент `SVC`), тому на
сервері це звичайний compose:

```bash
git pull
docker compose build api ws checkbox scheduler overseer
docker compose run --rm migrate up          # міграції окремим кроком
docker compose up -d api ws checkbox scheduler overseer
docker compose logs -f --tail=50 api
```

Порядок саме такий: **міграції окремо й до підняття сервісів**. У compose
вони описані як залежність, але запускати їх разом із рестартом означає
чекати на них у кожного сервіса окремо й не бачити помилку в окремому
виводі.

Скрипта з ssh навмисно немає. Написати його неважко, але непротестований
деплой-скрипт — це спосіб дізнатись про помилку в найгірший момент; коли
дроплет зʼявиться, скрипт напишемо на ньому й перевіримо.

### Що має бути в `.env` на сервері

Ті самі ключі, що в `.env.example`, і додатково — ті, без яких частина
сервісів мовчки нічого не робить:

| Ключ | Без нього |
|---|---|
| `JWT_PRIVATE_KEY` | рестарт api розлогінює всіх |
| `OPENAI_API_KEY` | чат кавенятка відповідає уривками бази знань |
| `NP_API_KEY` | scheduler не оновлює довідник і не трекає посилки |
| `CHECKBOX_LOGIN`/`PASSWORD` | checkbox не опитує чеки |
| `CHECKBOX_WEBHOOK_KEY` | вебхук відповідає 401 на все |
| `TELEGRAM_BOT_TOKEN`/`CHAT_ID` | overseer пише алерти лише в лог |

`.env.example` тримає тестові ключі Checkbox поруч зі справжніми навмисно —
щоб зменшити шанс випадково смикнути бойовий ПРРО.

## 2.1 Дроплет і файрвол через terraform

Сервер піднімає `infra/terraform`, не рука в панелі DigitalOcean: інакше
через місяць ніхто не скаже, звідки взялося правило файрвола. Токен
береться з `.env` (`DIGITALOCEAN_API_KEY`) обгорткою `scripts/tf.mjs` — у
лог і в аргументи процесу він не потрапляє.

```bash
make tf-plan      # що зміниться
make tf-apply     # дроплет, файрвол, привʼязка до проекту extrovert.cafe
make tf-output    # адреси й готова команда входу
make ssh-public   # зайти на сервер
```

Що описано: дроплет `extrovert-public` (1 vCPU / 2 ГБ, FRA1, Ubuntu 24.04)
зі swap-файлом на 2 ГБ і докером, файрвол `extrovert-public-fw` (вхідні
22, 2222, 80, 443, icmp) і привʼязка до проекту `extrovert.cafe`. Ключі
доступу — наш `keys/extrovert_ed25519` плюс ключі людей із акаунта
DigitalOcean за іменем (`ssh_key_names`). DO кладе ключі **лише при
створенні** дроплета: додати людину пізніше = дописати ключ у
`authorized_keys` руками.

**Чому ssh слухає ще й 2222.** З частини мереж вихідний 22 закритий —
21.09.2026 з робочої машини не відкривався навіть `github.com:22`. В
Ubuntu 24.04 ssh за замовчуванням запускає systemd через socket-активацію,
і директиву `Port` вона ігнорує; спроба додати порт у сам юніт сокета
перевірена на окремому дроплеті й закінчилась тим, що юніт лишився
`active`, не слухаючи **нічого** — навіть 22. Тому cloud-init вимикає
`ssh.socket` і вмикає класичний `ssh.service`, який `Port` розуміє.

**Головна пастка: user-data має бути тільки з ASCII.** DigitalOcean передає
cloud-init через config drive, і один не-ASCII символ — навіть у коментарі —
ламає його так, що cloud-init **мовчки не виконує нічого**: ні ssh на
запасному порту, ні докера, ні жодного повідомлення про помилку. Дроплет
при цьому здоровий і відповідає на 22. Доведено 21.09.2026 парою зондів:
мінімальний конфіг із єдиним рядком «# коментар кирилицею» не виконався,
той самий повний конфіг без не-ASCII — виконався цілком. Тому коментарі в
`cloud-init.yaml.tftpl` англійською, а пояснення «чому» — тут. Щоб це не
повторилось, у `main.tf` стоїть `precondition`, який валить `plan` з
поясненням, щойно в user-data зʼявиться не-ASCII.

**Пакети ставляться з `runcmd`, а не модулем `packages`.** Модуль пакетів
виконується до `runcmd`, а apt на першому завантаженні бореться за
dpkg-лок із власним `unattended-upgrade` образу — і весь цей час немає ні
ssh на запасному порту, ні докера. Тепер перший крок `runcmd` — ssh, і
лише потім apt (із `DPkg::Lock::Timeout`, щоб не падати на зайнятому локу).

Якщо сервер після створення мовчить — `terraform apply -var
debug_beacon=true`: перші 15 хвилин дроплет віддає на :80 стан cloud-init,
список портів і хвіст `cloud-init-output.log`, після чого вимикає це сам.

Стан terraform лежить локально й у git не їде (`infra/terraform/.gitignore`
пояснює чому). Наслідок памʼятати треба: `apply` із чистої копії репозиторію
підніме **другий** дроплет замість того, щоб побачити наявний. На новій
машині спершу `terraform import digitalocean_droplet.public <id>`.

Дві речі, які **не** робить terraform і які треба памʼятати: DNS на
`api.extrovert.cafe` і вміст `.env` на сервері.

## 2.2 Бакети R2

У Cloudflare створюються **чотири** бакети (EU jurisdiction), по одному на
призначення — `extrovert-pos`, `extrovert-video`, `extrovert-evidence`,
`extrovert-uploads`. Дев-копій у хмарі немає: локально їх замінює MinIO з
compose (`services.md` §2.1).

Разові налаштування, без яких воно не працює:

| Бакет | Що зробити |
|---|---|
| `extrovert-pos` | публічний доступ на читання + домен `pos.extrovert.cafe` |
| `extrovert-video` | lifecycle 7 днів + bucket lock на 7 днів |
| `extrovert-uploads` | **CORS**: `PUT` з `https://extrovert.cafe`, заголовок `content-type`. Lifecycle не заводимо: фото зі скарг живуть без обмеження (рішення власника 21.09.2026) |
| усі | ключ доступу лише для сервера; на машині розробника прод-ключів тримати не треба |

CORS для `extrovert-uploads` обовʼязковий: телефон заливає фото **напряму**
в бакет за підписаним посиланням, і без CORS браузер навіть не спробує.

## 3. Після першого викочування

- зареєструвати вебхук Checkbox (`POST /api/v1/webhook`) — потрібен
  `X-License-Key` каси; після цього `overseer` почне бачити
  `last_error_date` і скаржитись, коли вебхуки до нас не доходять;
- залити базу знань чату в OpenAI (`bun run kb:push`) — якщо переходимо з
  локального пошуку на `file_search`;
- перевірити, що `scheduler` справді публікує `outbox`: рядки з
  `published_at is null` не мають накопичуватись.
