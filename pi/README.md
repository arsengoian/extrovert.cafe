# Raspberry Pi — кіоск точки

Стан пристрою, звірено з живою малиною 18.08.2026: Raspberry Pi 1 Model B rev 2
(ARMv6), Raspbian 9 Stretch, **ядро 4.14.79**. `ssh pi@192.168.5.45`.

**Кіоск за замовчанням — `pos-native`, без X.** LXDE/lightdm вимкнені
(`systemctl set-default multi-user.target`), автозапуск — `pos-native.service`
(systemd, `WantedBy=multi-user.target`). Chromium-варіант (`archive/kiosk-chromium.sh`)
лишається робочим fallback'ом — розділ «Відкат на Chromium-кіоск» нижче.

Памʼять: `gpu_mem=128` у `/boot/config.txt` (виправлено 18.08.2026 — до того не
був заданий узагалі, тобто діяв дефолт 64 МБ, і `pos-native`'у бракувало
GPU-памʼяті під власну поверхню виводу — саме це, а не баг рендера, викликало
білий екран одразу після першого перемикання; постмортем у `../docs/roadmap.md`).
Не занижувати назад без причини — `vcgencmd get_mem malloc` мав 8 МБ вільних
при 64, притому що один 1080p RGBA-буфер важить ~8 МБ сам по собі.

⚠️ **Файли в цій теці — реконструкція з робочої сесії, а не дамп із пристрою.**
Перед тим як накочувати, звірити з тим, що реально лежить на Pi.

Уже спіймано на цьому: `kiosk.sh` на пристрої **не читав** `kiosk.env`, тож
`deploy.sh` підмінював URL у порожнечу, а кіоск тихо показував прод. Виправлено
17.08.2026 — на пристрій покладено версію з `kiosk.env` + `kiosk.extra`, стара
збережена в `~/backup-2026-08-09/kiosk.sh.pre-measure`. Реальний `kiosk.sh` ще
й гасить світлодіоди через `~/scripts/start.sh` і чекає мережу по `healthz` —
цього в реконструкції не було.

Повний опис налаштування: `../docs/raspberry-pi.md`.

### Прод: нативний рендерер (`pos-native`), без X — з 18.08.2026

`../pos-native/` — Cairo+GLES2 замінник браузера: малює ту саму сторінку
без zygote/GPU-процесів Chromium, прямо в dispmanx-шар, без X/LXDE. Архітектура
й вимір — `../docs/roadmap.md` («Перший запуск на реальному Pi 1», «Перемикання
проду»). **60 fps (vsync), ~19,5 % CPU, `GL_RENDERER=VideoCore IV HW`.**

Збирається нативно НА малині (`cd pos-native && make pi`, ~80 с), не
крос-компіляцією — на пристрої вже є gcc 6.3/glibc 2.24, під які інакше
довелось би підганяти sysroot. Одноразово перед першою збіркою:

```bash
sudo apt-get install libcairo2-dev libpango1.0-dev librsvg2-dev \
  libcurl4-openssl-dev libpng-dev libfontconfig1-dev \
  libgles2-mesa-dev libegl1-mesa-dev libraspberrypi-dev
```

(`*-mesa-dev` тут лише заради заголовків — GL/EGL лінкуються напряму на
Broadcom-ові `/opt/vc/lib/libbrcm{EGL,GLESv2}.so`, інакше `eglInitialize`
намагається піднятись як X11-клієнт і падає; деталі в коментарі над
`PKGS_BASE` у `pos-native/Makefile`.)

Автозапуск: `systemctl status pos-native` / `journalctl -u pos-native -f`.
Живий лог самого кіоска (не юніта) — `~/kiosk-native.log`. Конфігурація та
сама, що й у старого `kiosk.sh`: `~/kiosk.env` (точка, `POINT=`) і
`~/kiosk.extra` (руками, переживає перезапис).

**Граблі, які легко наступити знову:** зупиняти вже запущений X
(`systemctl stop lightdm` на живій сесії) кладе `bcm_host_init()` у стан,
який не знімає навіть `SIGKILL` — лікується тільки перезавантаженням. Якщо X
взагалі не стартував за це завантаження — усе працює миттєво й чисто. Тобто
будь-яке вимикання/увімкнення X **тільки через reboot**, не `stop`/`start`
на льоту. Подробиці — `../docs/roadmap.md`.

### Відкат на Chromium-кіоск

Якщо `pos-native` підвів на місці, а часу розбиратись немає:

```bash
ssh pi@192.168.5.45
sudo systemctl disable --now pos-native
sudo systemctl enable lightdm
sudo systemctl set-default graphical.target
crontab -l   # звірити watchdog-рядок нижче, замінити на chromium-варіант
sudo reboot
```

Watchdog-рядок на Chromium — у коментарі всередині `pi/crontab` (реконструкція,
секція «Стара версія»). `archive/kiosk-chromium.sh` і `deploy.sh` лишаються
робочими без змін — саме для цього сценарію.

## Годинник

У Pi 1 **немає RTC**. Після знеструмлення він піднімається з часом, збереженим
`fake-hwclock`, тобто з моменту останнього коректного вимкнення. Якщо дата
з᾿їхала на рік, ламається не лише статистика: **HTTPS до Cloudflare відвалюється**
(сертифікат «ще не дійсний»), і кіоск показує застарілі ціни з банером
«немає звʼязку». Симптом виглядає як проблема з мережею, а насправді — годинник.

```bash
./fix-clock.sh pi@192.168.5.45
```

## Замір: анімації + запис відео

Мета — з᾿ясувати, чи тягне Pi 1 одночасно кіоск з анімаціями і буферизацію
відеопотоку (`docs/video.md`). Запис нічого не декодує, це `-c copy`, тобто
перекладання вже стиснених пакетів у контейнер.

Кіоск має вбудований лічильник кадрів: `?hud=1` малює fps, мінімальний fps і
найгірший кадр у мілісекундах. Рівні анімацій перемикаються `?anim=0..4`:

| Рівень | Що рухається | Скільки елементів |
|---|---|---|
| 0 | нічого | — |
| 1 | поява карток, одноразова | 12 |
| 2 | + чашка дихає | 12 |
| 3 | + пара | +36 |
| 4 | + блиск по рідині, пульс цінника | +24 |

Окремо `?gpu=1` вмикає винесення анімованих елементів в окремі шари. На Pi 1 це
палиця з двома кінцями — менше перемальовування, але більше памʼяті під шари,
а її всього 384 МБ. Тому це перемикач, а не константа.

### Порядок

```bash
# 1. годинник
./fix-clock.sh

# 2. базовий рівень: кіоск без анімацій, без запису
ANIM=0 HUD=1 ./deploy.sh
#    подивитись на екран, записати fps

# 3. по одному рівню вгору: 1 → 2 → 3 → 4
ANIM=2 HUD=1 ./deploy.sh
ANIM=4 HUD=1 ./deploy.sh
ANIM=4 HUD=1 GPU=1 ./deploy.sh      # те саме з шарами
LEAN=1 ANIM=4 HUD=1 ./deploy.sh     # + Chromium у режимі економії

# 4. тепер додаємо відео. На ПК:
./cam-sim.sh
#    воно надрукує адресу виду rtsp://192.168.5.10:8554/cam1

# 5. на малині, паралельно з увімкненим кіоском:
ssh pi@192.168.5.45
CAM=rtsp://192.168.5.10:8554/cam1 MIN=20 ~/rec-test.sh
```

`rec-test.sh` пише CSV із %CPU ffmpeg, %CPU chromium, load average, вільною
памʼяттю, температурою, кількістю сегментів і обсягом буфера — раз на 10 секунд.
Наприкінці перевіряє `ffprobe` останні три сегменти: якщо вони читаються,
значить обраний контейнер (MPEG-TS) переживає обрив, як і замислювалось.

### Що вважати провалом

- fps у кіоску просідає нижче **24** або найгірший кадр перевалює **100 мс**
- вільної памʼяті лишається менше **40 МБ** — далі OOM-killer прибере Chromium
- температура вище **80 °C** — почнеться тротлінг
- ffmpeg не встигає: сегментів менше, ніж хвилин, або вони меншають

Будь-що з цього — беремо окремий вузол під запис і лишаємо Pi 1 самому кіоску.

### Результат заміру 17.08.2026

Пройдено, вузол не потрібен. Числа й застереження — у `../docs/roadmap.md`,
сирі CSV — у `measurements/`. Стисло: `anim=1` → 52 fps і під час запису теж,
`anim=2` і вище → 0,5 fps і 100 % CPU назавжди, `ffmpeg -c copy` → 4,3 % CPU,
20 сегментів із 20, температура максимум 63,8 °C.

### Граблі заміру — прочитати перед повторним прогоном

- **Чекати дві хвилини після завантаження сторінки.** Chromium тут осідає
  довго: замір через 45 с давав 1,6 fps там, де насправді 56.
- **Міряти без `?hud=1`.** Лічильник крутить вічний `requestAnimationFrame`,
  тобто сам замовляє кадри, яких у проді не буде, і тримає CPU на 90 %.
  Інструмент створює навантаження, яке міряє. Щоб зняти fps і не брехати собі —
  `--remote-debugging-port=9222` (через `~/kiosk.extra`) плюс `ssh -L 9222:...`
  і разовий `rAF`-лічильник ззовні. **Порт після заміру прибрати**: пристрій
  стоїть у публічному коридорі.
- **ffmpeg 3.2 на Stretch не вміє `-rtsp_flags listen`** — порт просто не
  біндиться, лог порожній. Це стосується лише серверного боку; клієнтський
  RTSP (те, що потрібно для камери) працює. `cam-sim.sh` тому запускається на
  ПК із сучасним ffmpeg, а не на малині.
- **`ffmpeg` мовчки падає з `Option rtsp_transport not found`**, якщо `CAM` не
  `rtsp://`. Полагоджено в `rec-test.sh`, але симптом виглядає як «замір
  пройшов, сегментів нуль».
- **`%CPU` у `ps` — середнє за весь час життя процесу**, а не поточне. Для
  Chromium, який працює годинами, колонка `chromium_cpu` у `rec-test.csv`
  показує 20 % там, де насправді 0,7 %. Миттєві значення рахуються по дельтах
  `/proc/<pid>/stat` — так зроблено в `measurements/sampler.csv`.
